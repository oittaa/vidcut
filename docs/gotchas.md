# Gotchas

Findings not recorded in the decision records ([decisions/](decisions/)).

- **wgpu's default error handler panics.** A texture larger than the device allows, or a binding of the wrong format, takes the GUI down: check sizes against `device.limits()` (`Screen::draw` draws black for a picture larger than the limit), and keep the shader's bindings and `Gpu::new`'s layout together.
- **egui-wgpu's native textures are `Rgba8Unorm` and shown as they are:** the viewer's target holds gamma-encoded BT.709 RGB, which egui puts on screen unchanged (no sRGB conversion).
- **`VideoReader::seek` drops every frame before its target** (`min_pts`), the keyframe it lands on too: a reader that only looked for the keyframe (`VideoFrames::keyframe_time`) calls `from_keyframe` to decode on from it, or it seeks again. And it decodes on to any frame up to the one it looked for, however far into the GOP: no keyframe lies between, where the usual one-second rule for decoding on would seek again.
- **FFmpeg 8.0 makes a GPU's H.264 decoder anew at every seek:** its H.264 decoder forgets its context on a flush (`h264_decode_flush`), so the next keyframe goes through `get_format` again, which tears the hwaccel down and creates another: 190–260 ms for 1080p on NVDEC. FFmpeg 9 keeps it: its log shows no `get_format` after a seek, and a seek to a keyframe of 1080p on NVDEC takes 31 ms (9.0.1). HEVC and AV1 keep theirs on both (seeks of 5–10 ms). A seek that flushes twice costs that twice. MP4 seeks by decode times, and with B-frames a keyframe is decoded before its own time: a target just before a keyframe (the last frame of a window back) lands on that keyframe, after the target. `VideoReader::seek` sees that in the first packet and seeks again before the decoder does anything.
- **Test cuts against fixtures with B-frames and real media**, not only small fixtures: encodes that decode a keyframe before the frames shown just ahead of it (open GOPs, x264's B-frames) are where readers lose frames at cuts.
- **Set packet durations explicitly when muxing** from delayed encoders (x264 with B-frames). Otherwise MP4 edit lists drop the last frame.
- **Clear a decoded frame's picture type before encoding it** (`set_kind(picture::Type::None)`). Encoders take it as an order: the output copies the source's keyframes, and x264 warns about every B-frame it can't make.
- **Matroska's demuxer exports content light levels only when MaxCLL and MaxFALL are both non-zero**, and FFmpeg's decoders put a container's HDR values on every frame unless the bitstream has its own: read a file's values from its first decoded frame, not from one place (`hdr::of_frame`).
- **FFmpeg's HEVC decoder puts the last HDR10+ it read on every frame after it** (8.0 and 9.0): HEVC whose HDR10+ SEIs stop partway decodes with the last one repeated, in decode order, so a frame without its own can't be told from one with it. AV1 frames from libdav1d (FFmpeg's CPU decoder for it) have only their own. A test reading HDR10+ back from HEVC output sees a missing one as the one before it.
- **`canonicalize` on Windows gives verbatim paths** (`\\?\C:\…`), which don't compare equal to the same path as people write it, and turn up in project files and messages: use `vidcut_core::dirs::canonical`, which keeps the usual form where it names the same file.
- **Project files keep relative paths with `/`** on every system (`store::portable`), and read them back with the system's separator: a project folder moves between Linux and Windows. Compare paths as `Path`s, not strings: on Windows `/` and `\` both separate, and `Path` equality knows it.
- **A Unix socket on Windows can't be woken by a shutdown:** a read waiting on it in one thread doesn't end when another thread shuts the socket down, so a cancelled client would wait forever. Live control uses named pipes there, read with overlapped calls (`ipc::transport`).
- **On Windows a process vidcut starts inherits every inheritable handle vidcut has open.** The C runtime's `fopen` opens files inheritable, and x264 opens its two-pass statistics files with it. While another process holds them x264 can't rename them: its first pass ends with `failed to rename`, and the second fails with `can't open stats file`. std's `Command` always starts a process this way, so Show in Folder asks the shell instead (`gui/file_manager.rs`), and a test that starts a process can break a two-pass export another test of the same binary runs. On Linux and macOS a process inherits only descriptors without close-on-exec, x264's among them, and a file another process has open can still be renamed.
- **Never give libplacebo the same Vulkan frame twice at once.** It takes a frame at the semaphore value FFmpeg's frame says and gives it back at the next one, so a frame held twice ends a step ahead of anything the GPU signals: FFmpeg, freeing it, waits for that value forever, and a transfer from CUDA can take its picture before it is there (`cuda::Blacks`, export.md §5).
- **FFmpeg drops an option an encoder doesn't have without a word:** `avcodec_open2` leaves it in the dictionary and opens anyway. `av1_vaapi` has no `qp` (its quantizer index is `global_quality`).
- **FFmpeg's Vulkan ProRes encoder works on one frame at a time:** `prores_ks_vulkan` (FFmpeg 9.0.2) makes its pool of GPU work with one slot, so `async_depth` changes nothing: 113 fps at 960×540 on the RTX 4080 SUPER, 31 on the Radeon iGPU, where `prores_ks` on frame threads makes about 300 here.
- **FFmpeg's Vulkan ProRes decoder crashes on AMD's Windows driver:** FFmpeg 9.0.2's `prores` decoder on Vulkan ended in a segfault on the Radeon iGPU every time, on one thread too. On the RTX 4080 SUPER it decoded 4K ProRes HQ at 512 fps on 0.6 ms of CPU a frame, against 31 fps and 33 ms on one CPU thread. vidcut doesn't use it.
- **FFmpeg's encoders use one thread unless given more:** `thread_count` (the `threads` option) is 1 for a program using the libraries, where the `ffmpeg` command sets it to automatic. libx264 hands it to x264 as its thread count; `prores_ks` and `dnxhd` use slice or frame threads only above 1. Proxies give ProRes and DNxHR frame threads (`proxy.rs`).
- **Intel's QSV runtime opens VA-API displays of its own,** outside FFmpeg's, to list what each GPU can do, and libva prints four info lines on stderr for each one. `main` sets `LIBVA_MESSAGING_LEVEL=1` (errors only) on Linux unless it is set.
- **AMD's video processor clips levels outside video range when told studio range:** below black and above white come out at 16 and 235 (chroma 16 and 240), 8 bits and 10, though nothing is converted. Told full range in and out instead, it keeps every level, so `hw::d3d11::Scaler` says full range where DXGI has such a space; PQ has studio range alone, and PQ's are clipped there. The scaler's check of its levels has bands below black and above white wherever the space keeps them.
- **FFmpeg's copy-down of Intel's VA-API frames is slow:** it reads a copy the driver makes of the surface (`vaGetImage`), 32 ms of a core for each 2160p P010 frame on an N150, where the surface mapped itself (`vaDeriveImage`) copies in 15 ms. `hw::download` maps Intel's surfaces itself, knowing the driver by libva's vendor string (FFmpeg's own sign of that driver, a quirk flag, isn't set for today's). Streaming loads (`MOVNTDQA`) made the copy slower there: the mapped surface is cached memory. It isn't everywhere: FFmpeg reads a copy because on Gen7–Gen9 the mapped memory is uncached, slow to read, and a card of its own (Arc) has the surface across the bus. So on each display both ways are timed on the first frames, four each, and the quicker kept (`hw::Ways`).
- **cpal's lookup of a device by its id misses ALSA's** (0.18): `device_by_id` adds a device number to the id it looks for (`sysdefault:CARD=PCH` becomes `sysdefault:CARD=PCH,DEV=0`), and the devices listed keep their ids without it, so a device chosen from the list played on the default without a word. `CpalOutput` finds the device among those listed, by its id as listed (`output_by_id`).
- **`AVHWDeviceContext.user_opaque` is FFmpeg's** for the devices `av_hwdevice_ctx_create` makes: VA-API keeps its DRM file there and frees it through that pointer.
- **AMD's Direct3D 11 decoder and VideoToolbox lose their way in H.264 sought into an open GOP.** From a keyframe that isn't IDR (x264 makes those with B-frames), AMD's decodes a few frames right, then shows one picture over and over. VideoToolbox (FFmpeg 9.0.2, MacBook Air M4) showed other frames after 9 of 90 seeks into the 90-frame fixture (`seek_check`): unreadable ones, and frames of the first GOP. Decoded from the start both are right, from an IDR keyframe too, and NVIDIA's Direct3D 11 and Intel's VA-API are right after a seek too. The CPU decodes H.264 with open GOPs there (`GpuDecoder::why_not`): `decode::h264_open_gop` reads the first keyframe and those at each fifth of the file. FFmpeg's x264 makes open GOPs when it makes B-frames, unless asked to close them. NVENC's H.264 and vidcut's proxies close theirs.
- **An untagged picture's matrix follows from its size** (`color::untagged_matrix`: BT.709 from 1280 wide or over 576 lines). A copy scaled on the GPU carries the matrix of the picture it was made from (`color::keep_matrix`): untagged 1280×720 shrunk to 640×360 otherwise read as BT.601, and the CPU's conversion to BT.709 took white 235 to 233.
- **FFmpeg's `scale_d3d11` doesn't work on AMD's driver:** its output textures are bound for the video encoder too (`D3D11_BIND_VIDEO_ENCODER`), which the driver refuses for NV12 and P010 (`E_INVALIDARG`). It also has no layout unless given `format=`, and scales the decoder's padding into the picture (1080p is decoded into 1088 lines). `hw::d3d11::Scaler` drives the video processor itself.
- **Take a frame's planes once, not per sample, and round without `f64::round` in loops over pixels.** ffmpeg-next's `frame::Video::data()` and `stride()` look the pixel format up on every call, and `f64::round` is a library call on baseline x86-64: measured light spent most of its time in them (`light::Samples`; a value not negative rounds with a half added and cut off).
- **libplacebo marks an input frame done before it has read it.** It's a libplacebo bug, fixed upstream in commit 2ba21c07 but not in any release yet. If libplacebo marks the frame done before the CUDA copy into it has finished:
  - libplacebo reads the old picture, so the export shows the previous frame;
  - the copy finishing late sets the frame's semaphore back by one, and FFmpeg waits forever when it frees the frame, so the export hangs.

  Workaround: `cuda::wait_done` waits for each copy to finish before the frame goes to libplacebo, and for libplacebo's output before the next copy. [The todo](todo/libplacebo-handback-workaround.md) says when to remove it.
- **macOS's `poll` reports a hang-up only on what it is asked for:** with `events` 0 it reports nothing at all, where Linux reports `POLLHUP` and `POLLERR` whatever is asked. Asked for `POLLIN`, a Unix socket hangs up already when the peer stops writing; asked for `POLLOUT`, once nothing can be sent, when the peer has closed (`ipc::transport::Stream::peer_gone`).
- **macOS threads don't inherit a QoS class:** a thread started by one in the utility class runs in the default one, like Windows's priorities and unlike Linux's idle class (`threads.rs`).
