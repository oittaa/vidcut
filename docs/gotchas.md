# Gotchas

Findings not recorded in the decision records ([decisions/](decisions/)).

- **wgpu's default error handler panics.** A texture larger than the device allows, or a binding of the wrong format, takes the GUI down: check sizes against `device.limits()` (`Screen::draw` draws black for a picture larger than the limit), and keep the shader's bindings and `Gpu::new`'s layout together.
- **wgpu 30's `Surface::configure` fails when another thread submits during it:** it waits for the device to go idle, and work submitted meanwhile fails it with "Failed to wait for GPU to come idle", a validation error the default handler panics on. eframe configures on every resize, so the viewer thread submits only through `gui/gate.rs` (preview.md §2).
- **egui-wgpu's native textures are `Rgba8Unorm` and shown as they are:** the viewer's target holds gamma-encoded BT.709 RGB, which egui puts on screen unchanged (no sRGB conversion).
- **`VideoReader::seek` drops every frame before its target** (`min_pts`), the keyframe it lands on too: a reader that only looked for the keyframe (`VideoFrames::keyframe_time`) calls `from_keyframe` to decode on from it, or it seeks again. And it decodes on to any frame up to the one it looked for, however far into the GOP: no keyframe lies between, where the usual one-second rule for decoding on would seek again.
- **FFmpeg 8.0 makes a GPU's H.264 decoder anew at every seek:** its H.264 decoder forgets its context on a flush (`h264_decode_flush`), so the next keyframe goes through `get_format` again, which tears the hwaccel down and creates another: 190–260 ms for 1080p on NVDEC. FFmpeg 9 keeps it, and HEVC and AV1 keep theirs on both. A seek that flushes twice costs that twice.
- **MP4 seeks by decode times.** With B-frames a keyframe is decoded before its own time, so a target just before a keyframe (the last frame of a window back) lands on that keyframe, after the target. `VideoReader::seek` sees that in the first packet and seeks again before the decoder does anything.
- **Test cuts against fixtures with B-frames and real media**, not only small fixtures: encodes that decode a keyframe before the frames shown just ahead of it (open GOPs, x264's B-frames) are where readers lose frames at cuts.
- **Set packet durations explicitly when muxing** from delayed encoders (x264 with B-frames). Otherwise MP4 edit lists drop the last frame.
- **Clear a decoded frame's picture type before encoding it** (`set_kind(picture::Type::None)`). Encoders take it as an order: the output copies the source's keyframes, and x264 warns about every B-frame it can't make.
- **Matroska's demuxer exports content light levels only when MaxCLL and MaxFALL are both non-zero**, and FFmpeg's decoders put a container's HDR values on every frame unless the bitstream has its own: read a file's values from its first decoded frame, not from one place (`hdr::of_frame`).
- **FFmpeg's HEVC decoder puts the last HDR10+ it read on every frame after it** (8.0 and 9.0): HEVC whose HDR10+ SEIs stop partway decodes with the last one repeated, in decode order, so a frame without its own can't be told from one with it. AV1 frames from libdav1d (FFmpeg's CPU decoder for it) have only their own. A test reading HDR10+ back from HEVC output sees a missing one as the one before it.
- **FFmpeg's decoders lend a frame what an earlier frame left in their context** (8.0): colors and the pixel aspect a frame's header gave stay in the `AVCodecContext`, and a later frame whose header leaves them out takes them (`fill_frame_props`, decode.c): PNG's cHRM, gAMA, sRGB and pHYs chunks, MJPEG's JFIF aspect. A frame's time (`best_effort_timestamp`) comes from the context's count of timestamps gone back so far (`guess_correct_pts`). A pool thread's decoder serves frames of many streams in no order (threads.md §4.2), so it gets the stream's colors and aspect back before each packet, and the reader guesses times itself in the stream's order (`decode/standalone.rs`).
- **MJPEG's and raw video's frames may lean on earlier packets,** though FFmpeg marks both codecs intra-only (8.0): MJPEG's decoder keeps the Huffman tables a frame defines for later frames that leave them out (mjpegdec.c), raw video's keeps the palette that comes once in a packet's side data, and SMV JPEG packs several frames in one packet. FFmpeg decodes none of them on frame threads, and neither does vidcut's pool: an intra-only codec decodes there only when FFmpeg runs it on frame threads (`decode/standalone.rs`). Image sequences decode there whatever their codec: each file is whole.
- **FFmpeg's PNG decoder holds on to its last picture** (8.0, for APNG's disposal) until its next frame or its close; a flush doesn't let it go. A decoder kept on each pool thread would hold a 4K 16-bit frame (50 MB) there, and its next frame couldn't reuse that one's planes (`buffers.rs`): reading a PNG sequence peaked 500 MB higher than on frame threads, and its frames stayed after the reader closed. A pool decoder that still holds the frame it gave closes after it (`decode/standalone.rs`): an open and close of FFmpeg's PNG decoder takes 2.6 µs.
- **`canonicalize` on Windows gives verbatim paths** (`\\?\C:\…`), which don't compare equal to the same path as people write it, and turn up in project files and messages: use `vidcut_core::dirs::canonical`, which keeps the usual form where it names the same file.
- **Project files keep relative paths with `/`** on every system (`store::portable`), and read them back with the system's separator: a project folder moves between Linux and Windows. Compare paths as `Path`s, not strings: on Windows `/` and `\` both separate, and `Path` equality knows it.
- **A Unix socket on Windows can't be woken by a shutdown:** a read waiting on it in one thread doesn't end when another thread shuts the socket down, so a cancelled client would wait forever. Live control uses named pipes there, read with overlapped calls (`ipc::transport`).
- **On Windows a process vidcut starts inherits every inheritable handle vidcut has open.** The C runtime's `fopen` opens files inheritable, and x264 opens its two-pass statistics files with it. While another process holds them x264 can't rename them: its first pass ends with `failed to rename`, and the second fails with `can't open stats file`. std's `Command` always starts a process this way, so Show in Folder asks the shell instead (`gui/file_manager.rs`), and a test that starts a process can break a two-pass export another test of the same binary runs. On Linux and macOS a process inherits only descriptors without close-on-exec, x264's among them, and a file another process has open can still be renamed.
- **Never give libplacebo the same Vulkan frame twice at once.** It takes a frame at the semaphore value FFmpeg's frame says and gives it back at the next one, so a frame held twice ends a step ahead of anything the GPU signals: FFmpeg, freeing it, waits for that value forever, and a transfer from CUDA can take its picture before it is there (`cuda::Blacks`, export.md §5).
- **FFmpeg drops an option an encoder doesn't have without a word:** `avcodec_open2` leaves it in the dictionary and opens anyway. `av1_vaapi` has no `qp` (its quantizer index is `global_quality`).
- **An encoder's own options come before the context's of the same name.** `avcodec_open2` looks a dictionary's option up in the encoder's own first, so `bf` sets `h264_amf`'s B-picture pattern, not the context's `max_b_frames`. FFmpeg 9.0.1's `h264_amf` reads only its own, never `max_b_frames`, so proxies give every encoder `bf=0` in its options (`ProxyEncoder::video_encoder`).
- **FFmpeg's Vulkan filters and encoders keep the last frames they read, but not those frames' frames context** (9.0.1, vulkan.c `ff_vk_exec_add_dep_frame`), until they are freed. Freed after the context's last owner, such a frame goes back to a freed context, and FFmpeg frees the frame through the freed memory (`vulkan_frame_free`): a crash where another thread took that memory meanwhile, so only now and then, with other threads at work. FFmpeg frees a graph's filters sources first, so vidcut's graphs of GPU frames free theirs downstream first (`hw::GpuGraph`). A Vulkan encoder has to close before the graph whose frames it takes.
- **FFmpeg's frame pools never shrink, and live as long as their last frame.** A decoder's frames come from its frames context's pool (`AVBufferPool`): NVDEC copies each frame out of its surfaces into a buffer of one (8.0, nvdec.c `real_hw_frames_ref`), VA-API's, Vulkan's and Direct3D 11's frames are its buffers, and a CPU decoder's come from pools of its own (get_buffer.c). A pool grows by the frames held at once, a frame let go goes back to it, and nothing is freed until the pool is, after the decoder and the last of its frames. So a kept picture holds its decoder's whole pool: a budget letting pictures go frees none of it, and a decoder closed (proxies switched, a cut to another file, a prepared picture's reader) keeps its peak beside the next one's while any of its pictures is kept. NVDEC's, Direct3D 11's and, where the driver has `vaCopy`, VA-API's kept pictures are copied into memory of their own (`cuda::keep`, `hw::Keeper`), and the CPU's decoders decode into buffers of vidcut's own (`buffers.rs`, a `get_buffer2` laying them out as FFmpeg's default does), into which the player copies a frame it keeps from any other pool. Mesa's VA-API and Vulkan's kept pictures stay their decoders' surfaces, and the store lets a pool's pictures go together (player.md §3).
- **Mesa's VA-API has no exact copy of a surface** (26.0, radeonsi): `vaCopy` is unimplemented, and its video processor converts colors on the way, P010 to P010 at the same size too: up to 9 levels off by default, and with explicit full range in and out, luma kept but 10-bit chroma 1.5 levels high (513.5 for 512). So on Mesa VA-API's kept pictures are the decoder's surfaces, in a pool its decoders share (`hw::vaapi::share_frames`). Intel's driver (iHD 26.1) has an exact `vaCopy`: 2.0 ms for a 4K NV12 frame and 3.3 ms for P010 on an N150, waited for, 0.15 ms to queue.
- **Intel's VA-API driver keeps surfaces let go until its next allocation** (iHD 26.1): a process's GPU memory (DRM fdinfo) stays where it was after kept pictures go, idle for seconds, and drops once the driver makes and lets go of surfaces again (more pictures kept). Measured, the memory a budget lets go shows up there late, not at once.
- **glibc keeps a freed frame's memory.** Its threshold for mapping a block of its own (128 KiB) rises to the largest block freed, up to 32 MiB, so once a frame is freed the next ones come from its heaps, which give little back. Two 1080p clips swapped under a 300 MB budget peaked 250 MB higher with planes from `av_buffer_alloc` than with planes mapped of their own (glibc 2.43). Mapped anew for each frame, decoding took a fifth more CPU, faulting their pages in (huge pages didn't help), so `buffers.rs` keeps the last 64 MB of planes let go for the next frames. A closed decoder's own memory (libdav1d's pool, its threads') stays in glibc's heaps all the same: `buffers::give_back` trims them (`malloc_trim`, on a thread of its own, at most once a second) when the player closes a decoder. Two AV1 clips decoded by libdav1d and swapped under a 500 MB budget settled 730–780 MB above the start in 24 swaps, where they grew past 900 MB in 8 without it.
- **`cuMemAlloc` rounds a picture up to 2 MiB:** a 960×540 P010 frame of FFmpeg's CUDA pool, 1.66 MB with its rows padded to the 512-byte texture alignment, takes 2 MiB (RTX 4080, driver 580), a third more than its samples; 4K takes 1% more. CUDA's stream-ordered allocator (`cuMemAllocAsync`) packs such pictures within 1.1%, and with its release threshold at 0, the default, gives their memory back once a stream is synchronized.
- **FFmpeg's Vulkan ProRes encoder works on one frame at a time:** `prores_ks_vulkan` (FFmpeg 9.0.2) makes its pool of GPU work with one slot, so `async_depth` changes nothing.
- **NVIDIA's Windows driver has one NT handle per memory object:** every `vkGetMemoryWin32HandleKHR` of the same memory gives the same handle. Closed, it is gone for the exports after it: an import of it fails with `VK_ERROR_OUT_OF_DEVICE_MEMORY`, and its value may name another handle by then. Open, it keeps the memory after `vkFreeMemory`. So vidcut exports each of FFmpeg's memory objects once and closes the handle when FFmpeg frees the frames context, after the memory (`hw::vulkan`). FFmpeg's own copy of a frame to CUDA exports the same handle, and closes it when it frees the frame.
- **FFmpeg's Vulkan ProRes decoder crashes on AMD's Windows driver:** FFmpeg 9.0.2's `prores` decoder on Vulkan ends in a segfault on the Radeon iGPU, on one thread too. vidcut decodes on Vulkan on NVIDIA's GPUs only (`GpuDecoder::why_not`). A crash can't be caught, so allowing another vendor takes its own check first.
- **SVT-AV1 leaves stale blocks in low delay at its fast presets** (`pred-struct=1`): where a few flat blocks of a picture change, it codes some of them, from 16×32 to a whole barcode cell, as they were in the frame before, at any CRF (10 too), in 8 and 10 bits. dav1d and libaom decode the same. 2.3.0 (Ubuntu's, for FFmpeg 8.0) does it from preset 9 up, and makes low-delay presets below 7 into 7; no option tried helps it at 10 (variance boost, tune, AQ, loop filters, `rtc`). 4.2.0, the newest, does it from 10 up, which it warns may show artifacts outside its RTC mode, and in RTC mode (`rtc=1`) from 11 up. Proxies use preset 8 (`ProxyEncoder::options`), about 1.7× the CPU time of preset 10. There 2.3.0 can show a 1280×720 barcode cell that changes along with others at two thirds of its new level for one frame (its mean coarsely quantized, not the frame before), and the barcode still reads.
- **FFmpeg's encoders use one thread unless given more:** `thread_count` (the `threads` option) is 1 for a program using the libraries, where the `ffmpeg` command sets it to automatic. libx264 hands it to x264 as its thread count; `prores_ks` and `dnxhd` use slice or frame threads only above 1. Proxies give ProRes and DNxHR frame threads (`proxy.rs`).
- **Intel's QSV runtime opens VA-API displays of its own,** outside FFmpeg's, to list what each GPU can do, and libva prints four info lines on stderr for each one. `main` sets `LIBVA_MESSAGING_LEVEL=1` (errors only) on Linux unless it is set.
- **AMD's video processor clips levels outside video range when told studio range:** below black and above white come out at 16 and 235 (chroma 16 and 240), 8 bits and 10, though nothing is converted. Told full range in and out instead, it keeps every level, so `hw::d3d11::Scaler` says full range where DXGI has such a space; PQ has studio range alone, and PQ's are clipped there. The scaler's check of its levels has bands below black and above white wherever the space keeps them. Where a single pass fails that check, as the Radeon iGPU's does on a shrink to less than half each way (4K to 960×540: level 4 comes out 20), the scaler shrinks in halving passes, each checked. A GPU whose single pass passes keeps it. A turned pass is checked turned, as it is drawn: the Radeon keeps every level turning 4K a quarter into 720×1280 in one pass, but not shrinking 4K into 1280×720 unturned, the same shrink.
- **FFmpeg 9's `scale_cuda` truncates in every pass of a shrink:** it shrinks with filters (`use_filters`, on by default for a shrink), a horizontal and a vertical pass that each cast their sum to an integer (`from_floatN`, vector_helpers.cuh). Through vidcut's halvings, 4K shrunk to 192×108 came out 8 to 9 levels low in red and blue, 2 to 3 at 960×540. Its fixed kernels round the average of four pixels, as FFmpeg 8's do. Asked for with `use_filters=0` (`cuda::scaling`), the pictures are within 1.2 levels of the CPU's at 192×108 and 0.5 at 960×540.
- **FFmpeg's GPU deinterlacers aren't `bwdif` to the level** (9.0.1), so both fail the check that would trust them (`hw::deinterlace`, export.md §4), and interlaced frames NVDEC and Vulkan decode come down for `bwdif`. They give its frames and timestamps. `bwdif_vulkan` reads black past the top and bottom edges and doesn't clip to the frame's bits: on 10-bit ProRes the field's rebuilt rows at the edges go wrong, the outermost at half its level (470 for 940) and the next ones overshooting (1053), and white edges reach 1045 where `bwdif` stops at 1023. Elsewhere it is within a code. `bwdif_cuda` differs by up to 115 levels of 8 bits, at sharp moving edges and in the top row, on the interlaced H.264 fixture. Its kernel has no filter of its own for the rows at the edges, and where `bwdif` adds the next field's rows 4 above and 4 below, it adds the row 4 above twice (`next2_mrefs4`). `bwdif` itself mirrors the rows past an edge and has a filter of its own for the four rows nearest it. Reported upstream with patches: code.ffmpeg.org issues 25105 (`bwdif_cuda`) and 25106 (`bwdif_vulkan`).
- **FFmpeg's copy-down of Intel's VA-API frames is slow:** it reads a copy the driver makes of the surface (`vaGetImage`), 32 ms of a core for each 2160p P010 frame on an N150, where the surface mapped itself (`vaDeriveImage`) copies in 15 ms. `hw::download` maps Intel's surfaces itself, knowing the driver by libva's vendor string. On Gen7–Gen9 the mapped memory is uncached and slow to read, and a card of its own (Arc) has the surface across the bus, so on each display both ways are timed on the first frames, four each, and the quicker kept (`hw::vaapi::Ways`).
- **cpal's lookup of a device by its id misses ALSA's** (0.18): `device_by_id` adds a device number to the id it looks for (`sysdefault:CARD=PCH` becomes `sysdefault:CARD=PCH,DEV=0`), and the devices listed keep their ids without it, so a device chosen from the list would play on the default without a word. `CpalOutput` finds the device among those listed, by its id as listed (`output_by_id`).
- **`AVHWDeviceContext.user_opaque` is FFmpeg's** for the devices `av_hwdevice_ctx_create` makes: VA-API keeps its DRM file there and frees it through that pointer.
- **AMD's Direct3D 11 decoder and VideoToolbox lose their way in H.264 sought into an open GOP.** From a keyframe that isn't IDR (x264 makes those with B-frames), AMD's decodes a few frames right, then shows one picture over and over. VideoToolbox (FFmpeg 9.0.2) shows other frames after some seeks (`seek_check`). Decoded from the start both are right, from an IDR keyframe too. The CPU decodes H.264 with open GOPs there (`GpuDecoder::why_not`): `decode::h264_open_gop` reads the first two keyframes and the first from each fifth of the file, by bytes where the file has no duration (raw H.264), and says open when a seek or a read fails or no keyframe after the first turns up. FFmpeg's x264 makes open GOPs when it makes B-frames, unless asked to close them. NVENC's H.264 and vidcut's proxies close theirs.
- **The backward buffer counts 3 bytes a pixel** (`VideoFrames::reversed_frames`). A 10-bit 4:2:2 picture takes 4, so a reversed clip's ProRes pictures take a third more than `REVERSED_BYTES`.
- **An untagged picture's matrix follows from its size** (`color::untagged_matrix`: BT.709 from 1280 wide or over 576 lines). A copy scaled on the GPU carries the matrix of the picture it was made from (`color::keep_matrix`), or untagged 1280×720 shrunk to 640×360 would read as BT.601.
- **Tell FFmpeg's `buffer` source a picture's matrix and range** (`colorspace`, `range`). A conversion FFmpeg adds by itself, for a filter that doesn't take the layout, reads the frame's own tags and writes the source's. Told nothing, the source makes it convert to BT.601's matrix. `transpose` takes no 4:2:2, so a BT.709 4:2:2 picture turned a quarter would come out in other colors. The Normalizer tells its source and each frame the matrix and range it reads the picture with (`color::Source::yuv_tags`).
- **FFmpeg's `scale_d3d11` doesn't work on AMD's driver:** its output textures are bound for the video encoder too (`D3D11_BIND_VIDEO_ENCODER`), which the driver refuses for NV12 and P010 (`E_INVALIDARG`). It also has no layout unless given `format=`, and scales the decoder's padding into the picture (1080p is decoded into 1088 lines). `hw::d3d11::Scaler` drives the video processor itself.
- **Take a frame's planes once, not per sample, and round without `f64::round` in loops over pixels.** ffmpeg-next's `frame::Video::data()` and `stride()` look the pixel format up on every call, and `f64::round` is a library call on baseline x86-64 (`light::Samples`: a value not negative rounds with a half added and cut off).
- **libplacebo marks an input frame done before it has read it** (fixed in commit 2ba21c07, in no release yet). If it does so before the CUDA copy into the frame has finished, the export shows the previous frame, or it hangs: the copy finishing late sets the frame's semaphore back by one, and FFmpeg waits forever when it frees the frame. Workaround: `cuda::wait_done` waits for each copy to finish before the frame goes to libplacebo, and for libplacebo's output before the next copy. [The todo](todo/libplacebo-handback-workaround.md) says when to remove it.
- **macOS's `poll` reports a hang-up only on what it is asked for:** with `events` 0 it reports nothing at all, where Linux reports `POLLHUP` and `POLLERR` whatever is asked. Asked for `POLLIN`, a Unix socket hangs up already when the peer stops writing; asked for `POLLOUT`, once nothing can be sent, when the peer has closed (`ipc::transport::Stream::peer_gone`).
- **macOS threads don't inherit a QoS class:** a thread started by one in the utility class runs in the default one, like Windows's priorities and unlike Linux's idle class (`threads.rs`).
