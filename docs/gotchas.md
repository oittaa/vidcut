# Gotchas

This file lists the FFmpeg, driver, OS, library and Resolve behavior that vidcut works around. Each item gives the quirk, what it breaks, and the code that handles it. [design/](design/README.md) tells how vidcut is built.

## wgpu and egui

- **wgpu's default error handler panics.**
  - A texture larger than `device.limits()` allows, or a binding of the wrong format, stops the GUI.
  - `Screen::draw` draws black for a picture past the limit.
  - The bindings of the shader change together with the layout in `Gpu::new`.
- **wgpu does not let a pipeline draw into `R16Unorm` or `Rg16Unorm` by default.**
  - The 16-bit unorm feature lets a shader read these formats, but not draw into them.
  - Thus the device also asks for the GPU's own format features (`TEXTURE_ADAPTER_SPECIFIC_FORMAT_FEATURES`). Then wgpu permits what the GPU can do. Metal can draw into these formats.
  - Without them, a pipeline or a view that draws into these formats is a validation error, and the default handler panics.
  - The encoding finds the pipeline before it makes the view.
  - Thus `Encoders::new` makes each pipeline of the encoding under an error scope (`checked`). It keeps the pipelines that the device takes.
  - The VideoToolbox hand-off draws 10-bit planes into `R16Unorm` and `Rg16Unorm` IOSurfaces. Without these pipelines, those planes go through memory (`through_memory`).
- **wgpu 30's `Surface::configure` fails when another thread submits while it waits for the device to go idle**.
  - Then the default handler panics.
  - eframe configures on each resize. Thus the viewer thread submits through `Gate::pass` ([playback](design/playback.md#the-viewer-thread), [todo](todo/wgpu-configure-gate.md)).
- **wgpu 30 compares two devices by their id only.**
  - Each wgpu instance counts its ids from the start. Thus the viewer's device and the offscreen device can have the same id.
  - Then `==` says that they are one device. wgpu looks for the buffer of one device in the other, and panics.
  - Thus each `Gpu` has its own id, and a held picture compares that id (`Held::on`).
- **wgpu 30 drops the errors of a lost device.**
  - A GPU can stop. For example, Windows resets a GPU when one piece of work runs for more than 2 seconds (TDR).
  - Then wgpu marks the device lost. It drops each error of the type `DeviceLost`, and does not call the error handler.
  - A buffer made after the loss is invalid. Its next use is a validation error, and the default handler panics.
  - `create_buffer_init` panics on a lost device too, because it unwraps the mapped range.
  - Thus the off-screen device watches for its loss (`Offscreen::watch`). After the loss, its error handler logs the errors and does not panic.
  - `compute::buffer_with` fills a new buffer without that unwrap.
- **On Metal, threads that write different components of one vector in workgroup memory can give wrong results.**
  - On an Apple M4 (macOS 27.2), four threads wrote the four components of one `vec4` in workgroup memory. The convolutions then gave wrong results.
  - Vulkan on an NVIDIA GPU gave correct results with the same shaders.
  - Thus `CONV`, `CONV4` and `WINO_GEMM` write whole vectors into workgroup memory. Then they match onnxruntime on the M4.
  - `scripts/face-check.py` finds the first wrong step of the slow face model ([tools](tools.md)).
- **Windows stops the computer after more than five GPU resets in one minute** (bug check 0x116, `TdrLimitCount` and `TdrLimitTime`).
  - Thus vidcut makes a new device after a loss only on an action of the user, and only a few times in a minute (`screen::retry_lost`).
- **egui-wgpu shows an `Rgba8Unorm` native texture's values as they are**, with no sRGB conversion.
  - The target of the viewer (`TARGET` in `screen/mod.rs`) holds gamma-encoded BT.709 RGB.
- **egui does not give the native handles of its viewports.** eframe gives only the handle of the main window (`Frame`).
  - The owner and the placement of a separate window need its handle.
  - Thus on Windows, `Tool::watch` finds a separate window by its title among the windows of the UI thread (`native::find`).
- **egui gives a window screenshot only after one more frame.**
  - `request_screenshot` draws the window into a texture and reads it back from the GPU. The read-back finishes in a later frame.
  - egui does not draw that frame by itself. A window with nothing to change draws no frame, so the picture does not arrive.
  - Thus the GUI asks for new frames while a window capture waits (`Capturing`).

## FFmpeg: reading and decoding

- **FFmpeg on Windows opens files without delete sharing** (8.0, 9.0: `_wsopen` with `SH_DENYNO` in file_open.c).
  - While FFmpeg reads a file, nothing can rename, move or delete the file or its folder.
  - Thus a media file or a proxy that vidcut plays cannot go away and come back, as it can on other systems ([missing media](design/live.md#missing-media)).
  - `decode::open_file` opens the file with std's `File`, which shares delete. It gives the file to FFmpeg as a `StreamIo`.
- **MP4 seeks by decode times, and FFmpeg 8.0 makes a GPU's H.264 decoder anew at every flush.**
  - With B-frames, a keyframe decodes before its own time. Thus a seek to just before the keyframe lands on that keyframe, after the target.
  - FFmpeg 8.0's H.264 decoder forgets its hardware context on a flush. The next keyframe builds another context (190–260 ms for 1080p on NVDEC).
  - FFmpeg 9 keeps the context. HEVC and AV1 keep it in both versions.
  - `VideoReader::seek` checks the first packet, and seeks again before it flushes. Thus a seek flushes once.
- **Matroska exports content light levels only when MaxCLL and MaxFALL are both non-zero**.
  - Decoders put the HDR values of the container on each frame whose bitstream has none.
  - `hdr::of_frame` reads the values of a file from its first decoded frame.
- **FFmpeg's HEVC decoder puts the last HDR10+ it read on every frame after it** (8.0, 9.0), in decode order.
  - A frame without its own HDR10+ looks like a frame with it.
  - libdav1d's AV1 frames carry only their own HDR10+.
  - A test that reads HDR10+ back from HEVC sees a missing one as the one before ([todo](todo/hdr-metadata-more.md)).
- **FFmpeg's decoders lend a frame what an earlier frame left in their context** (8.0, `fill_frame_props` in decode.c).
  - This includes colors and pixel aspect: PNG's cHRM, gAMA, sRGB and pHYs, and MJPEG's JFIF aspect.
  - It also includes the time guess (`guess_correct_pts`).
  - The decoder of a pool thread serves many streams in no order ([threads](design/threads.md#the-cpu-pools)).
  - Thus `decode/standalone.rs` gives the decoder the colors and the aspect of the stream before each packet (`Kind::restore`).
  - It also guesses the times itself, in stream order.
- **MJPEG and raw video frames may lean on earlier packets**, though FFmpeg marks both intra-only (8.0).
  - Examples: MJPEG's Huffman tables, a palette of raw video that is sent once, and the several frames in a packet of SMV JPEG.
  - FFmpeg decodes neither on frame threads.
  - `standalone::stands_alone` sends an intra-only codec to the pool only where FFmpeg decodes it on frame threads.
  - Image sequences go to the pool, whatever their codec.
- **FFmpeg's PNG decoder holds its last picture** (8.0, for APNG) until its next frame or its close.
  - A flush does not free the picture.
  - Kept on each pool thread, the decoder would hold a frame there (50 MB at 4K 16-bit).
  - A pool decoder that still holds the frame that it gave closes after it gives that frame (`decode/standalone.rs`).
- **FFmpeg's frame pools never shrink, and live until their last frame.**
  - The frames of each decoder come from a pool (nvdec.c, get_buffer.c, the GPU frames contexts).
  - The pool grows to the number of frames held at once. FFmpeg frees it after the decoder and its last frame.
  - Thus one kept picture holds the whole pool of its decoder.
  - Also, the peak of a closed decoder stays beside the peak of the next decoder.
  - `hw::Keeper` copies the kept pictures of NVDEC, Direct3D 11 and VA-API (with `vaCopy`) into memory of their own.
  - CPU decoders decode into vidcut's buffers (`buffers.rs`, its `get_buffer2`).
  - The kept pictures of Mesa VA-API and Vulkan stay pool surfaces. `Store::evict` lets the pictures of a pool go together ([playback](design/playback.md#the-engine)).
- **FFmpeg's `exr` decoder fails on most float PIZ files** (9.0.1, 9.0.2; master has the same code).
  - It makes the Huffman table of PIZ with FFmpeg's VLC tables (vlc.c). There, the index of a subtable is a 16-bit integer.
  - PIZ splits each float sample into two 16-bit halves. In a real picture the low halves are noise. Thus one block uses almost all 65536 codes.
  - The table then needs more than 32767 entries. The build stops with "strange codes", and each block fails.
  - FFmpeg returns the frame all the same, with the failed blocks not filled, and no error.
  - Smooth gradients and half floats decode correctly. Thus the fault depends on the picture, not on its size. Renders of Resolve Studio 21.2 fail too.
  - Thus vidcut decodes each OpenEXR with the `exr` crate ([design/gpu.md](design/gpu.md#the-gpu-and-the-decoder)).
- **FFmpeg's scaler cuts floats to 0 to 1, in steps of 16-bit numbers** (9.0.2).
  - Each conversion from a float format does this, also into another float format.
  - `grayf32le` at 2.5 gives 1.0 in `gbrpf32le`.
  - `gbrpf32le` at 2.5, 0.5 and −0.25 gives 0.99979, 0.50016 and 0 in `gbrapf32le`.
  - The `exr` decoder gives `gbrpf16le` for half floats. `ffmpeg -pix_fmt gbrpf32le` cuts them too. Thus a test of a half file compares the `gbrpf16le` samples.
  - Thus `Relayout` gives no float picture to the scaler ([playback](design/playback.md#gpu-pictures)).
- **FFmpeg 8 has no demuxer or decoder for an animated WebP** (8.0.1). FFmpeg has them from 9.0.
  - FFmpeg 8 reads the file with `webp_pipe`, as one image that it cannot decode. An animated WebP of one frame gives the same result.
  - Without a check, the file comes in as a still of 2×2 pixels, and its picture never renders.
  - Thus `probe` refuses a file that `webp_pipe` reads, when the animation flag of its VP8X chunk is on (`animated_webp`). The message says that the file needs FFmpeg 9.0.
  - FFmpeg 9 reads a file with this flag with `webp_anim`. Thus the refusal does not occur there.
- **FFmpeg makes up a frame rate for a stream whose file states none** (9.0.1, `avformat_find_stream_info`).
  - An example is a Matroska file without a frame duration in its track (`DefaultDuration`).
  - A 60 fps HEVC stream with timestamps in milliseconds gets 62.5 fps (125/2).
  - A 60 fps AV1 stream of 4K frames gets no average rate, and 1000 fps as its other rate. 1000 is one over the time base.
  - Thus `probe` measures the rate of such a file from its timestamps ([model](design/model.md)).
- **`AVHWDeviceContext.user_opaque` is FFmpeg's** on the devices that `av_hwdevice_ctx_create` makes.
  - VA-API keeps its DRM file there, and frees the file through that pointer.
  - vidcut uses the field only on the CUDA devices that it allocates itself (`CudaDevice::with_own_stream`).
- **ffmpeg-next's `frame::Video::data()` and `stride()` look the pixel format up on every call**.
  - Also, `f64::round` is a library call on baseline x86-64.
  - Loops over pixels take the planes once, and round by adding a half and truncating (`light::Samples`).

## FFmpeg: filters and colors

- **FFmpeg's resampler refuses a layout with top front left and no top front right.**
  - The first 13 channels of the 22.2 layout have this form. The export then fails with `cannot convert audio`.
  - Thus `channel_layout` uses top front center in place of top front left at 13 channels.
- **FFmpeg's resampler puts a mono input on each side of a stereo output at −3 dB** (9.0.1, `swr_build_matrix2`).
  - The coefficient is a fixed 0.7071. The center mix level does not change it.
  - Thus `Resampler::new` sets a matrix of 1 for each side (`swr_set_matrix`).
  - A mix of three channels or more keeps the default matrix.
- **FFmpeg's `buffer` source takes the frame it is given** (`av_buffersrc_add_frame`, which ffmpeg-next's `Source::add` calls).
  - It moves the buffers out of the frame, and leaves the frame empty.
  - Thus `hw::run_graph` gives the graph of a turn a reference of its own (`av_frame_ref`).
- **FFmpeg's scaler makes RGB and gray of more than 8 bits too bright when it converts them to YUV** (9.0.1, `scale`).
  - The top of an input of N bits acts as 255 × 2^(N-8), not as 2^N - 1.
  - Thus luma and chroma have a gain: 1.0039 at 16 bits, 1.0037 at 12 bits, 1.0029 at 10 bits.
  - Limited and full range have the same gain. In full range, the top of the range also clips.
  - RGB and gray of 8 bits have no gain.
  - Thus `Relayout` keeps these pictures as RGB (`gbrp16le`, `gbrap16le`).
- **FFmpeg's scaler does not reach the top of `gbrp16le` from planar RGB or gray of fewer bits** (9.0.1, `scale`).
  - From `gbrp` forms, the top code gives 65408 at 9 bits, 65473 at 10 bits, 65520 at 12 bits and 65534 at 14 bits.
  - The conversion through `rgb48le`, `rgba64le` or `gray16le` gives 65535 at each of these depths.
  - Thus `Relayout` converts a picture of 9 to 15 bits through these forms.
- **FFmpeg's scaler ignores the range of a gray input** (9.0.1, `scale`). It reads the codes as full range, with a tag or `in_range`. Thus vidcut reads all gray in full range.
- **FFmpeg's GPU deinterlacers aren't `bwdif`** (9.0.1).
  - `bwdif_vulkan` reads black past the top and bottom edges, and does not clip to the bits of the frame.
  - Thus its 10-bit edge rows come out at half level, or overshoot.
  - `bwdif_cuda` differs by up to 115 levels at moving edges and in the top row.
  - `bwdif_cuda` has no filter for the edge rows, and adds the row 4 above twice (`next2_mrefs4`).
  - `hw::deinterlace` checks each deinterlacer against `bwdif` once in each process.
  - Both fail. Thus their interlaced frames come down to memory for `bwdif`.
  - The upstream reports, with patches, are code.ffmpeg.org issues 25105 and 25106 ([todo](todo/gpu-deinterlacers-check.md)).
- **FFmpeg's Vulkan filters and encoders keep the frames they last read, but not those frames' frames context** (9.0.1, vulkan.c `ff_vk_exec_add_dep_frame`).
  - If such a frame is freed after the last owner of its context, it is freed through freed memory (`vulkan_frame_free`).
  - This causes a crash now and then.
  - FFmpeg frees the filters of a graph sources first. Thus `hw::GpuGraph` frees them downstream first.
  - A Vulkan encoder closes before the graph whose frames it takes.

## FFmpeg: encoding and muxing

- **FFmpeg's Vulkan ProRes encoder works on one frame at a time:**
  - `prores_ks_vulkan` (9.0.2) makes its pool of GPU work with one slot. Thus `async_depth` changes nothing.
  - vidcut does not set `async_depth`.
- **ProRes has a green right edge at a width of 16n + 1:**
  - `prores_ks` files of 1281 and 1297 wide have a green last column. A file of 1283 wide does not.
  - Resolve Studio 21.1.2 reads the green in the file from vidcut. Its own ProRes file of 1281 wide has the same edge.
  - vidcut keeps the size and writes this edge.
- **FFmpeg's `tiff` encoder tags each alpha as straight:**
  - FFmpeg 9.0.1 writes ExtraSamples 2 (unassociated alpha) in each TIFF with alpha, also for premultiplied colors.
  - `FrameFiles` changes the tag to 1 (associated alpha) for Premultiplied.
- **FFmpeg's `exr` encoder cuts half floats toward zero:**
  - FFmpeg 9.0.2 drops the low bits of a 32-bit float to make a half float. 0.50044 becomes 0.5, not 0.50049.
  - OpenEXR and Resolve Studio 21.2 round to the nearest half float.
  - The encoder also has only `none`, `rle`, `zip1` and `zip16`, and it writes no `timeCode`.
  - Thus vidcut does not use it. FFmpeg's `rawvideo` encoder gives the planes, and the `exr` crate writes the file ([design/export.md](design/export.md#encoding-one-output)).
- **Set packet durations when muxing from an encoder with delay** (x264 with B-frames).
  - If you do not, the edit list of MP4 drops the last frame (`VideoOut::drain`).
- **Clear a decoded frame's picture type before encoding it** (`set_kind(picture::Type::None)`).
  - Encoders take the picture type as an order.
  - Then the output copies the keyframes of the source, and x264 warns of each B-frame that it cannot make.
- **FFmpeg drops an option an encoder doesn't have without a word:**
  - `avcodec_open2` leaves the option in the dictionary, and opens the encoder anyway.
  - `av1_vaapi` and `vp9_vaapi` have no `qp`. `encode::vaapi_options` gives them `global_quality`.
- **An encoder's own options come before the context's of the same name.**
  - `bf` sets `h264_amf`'s own B-frame option, not `max_b_frames`.
  - FFmpeg 9.0.1's `h264_amf` never reads `max_b_frames`.
  - Proxies give each encoder `bf=0` (`ProxyEncoder::video_encoder`).
- **FFmpeg's encoders get one thread unless told otherwise**.
  - `thread_count` is 1 for a program that uses the libraries. The `ffmpeg` command sets it to automatic.
  - `encode::open_options` gives each CPU encoder `threads=auto`.
  - `dnxhd` then takes frame threads, each with its own rate-control table (266 MB at 2160p).
  - Thus `dnxhd` gets `thread_type=slice`, which shares one table.
  - `prores_ks` keeps frame threads. Its slice threads only search quantizers, and take 1.5 times as long.
- **SVT-AV1 leaves stale blocks in low delay at its fast presets** (`pred-struct=1`).
  - Where a few flat blocks change, it codes some of them as they were in the frame before, at any CRF.
  - 2.3.0 (Ubuntu's, with FFmpeg 8.0) does this from preset 9 up.
  - 4.2.0 does this from preset 10 up (11 with `rtc=1`).
  - Proxies use preset 8 (`ProxyEncoder::options`).
- **An encoder takes no frame after it is drained:**
  - After the end of the stream, `avcodec_send_frame` gives `AVERROR_EOF`.
  - Thus each run of encoded frames between two copied runs gets a new encoder (`Reopen`).
- **With the global header flag, x264 and NVENC put the SPS and PPS only into the extradata:**
  - A packet in the middle of the stream then has no parameter sets. A decoder cannot start a run of frames there.
  - The first packet of each run, copied or encoded, gets the parameter sets of its extradata (`bypass::Bits`).
- **The MP4, MOV and Matroska muxers rewrite Annex B packets:**
  - When the extradata of an H.264 or HEVC stream is Annex B, they write each NAL unit with its length before it.
  - Copied packets become Annex B, as the packets of the encoder are. Thus one stream holds both.
- **An H.264 key packet is not always an IDR:**
  - A MOV file can mark an I-frame with a recovery point as a key frame. The frames after it can use frames before it (an open GOP).
  - A copy of H.264 starts only at a packet with an IDR slice (`bypass::Bits`).
- **SVT-AV1 marks only its first frame as a key packet:**
  - SVT-AV1 4.2.0 makes forward key frames. The `libsvtav1` encoder of FFmpeg 9.0 gives them no key flag.
  - Thus a copy of such a file starts only at its first frame.
- **FFmpeg decodes ProRes 4444 and 4444 XQ at 12 bits:**
  - The `prores` decoder of FFmpeg 9.0 gives `yuv444p12le` or `yuva444p12le` for these profiles. `prores_ks` takes 10 bits.
  - The ProRes frame header has no bit depth. Thus a ProRes file matches by its profile, chroma and alpha, not by its bits.

## GPU drivers

- **A GPU can cut a float toward zero when it writes a half float** (NVIDIA GeForce RTX 4080 SUPER, Windows, driver 32.0.16.2140).
  - The render cache in Uncompressed 16-bit Float writes each 32-bit value into an `R16Float` target (`fs_encode_float`).
  - In a test of 196,608 random values, each value that a half float cannot hold came out closer to zero.
  - OpenEXR rounds to the nearest half float.
  - Thus the shader rounds each value to the nearest half float first (`half_rounded`). The GPU then writes that value exactly.
- **NVIDIA's exit handlers break a close during the exit** (Linux, driver 580).
  - The handler of libnvcuvid runs from `_dl_fini`. If a decoder still lives, the handler joins a thread of the library.
  - A decoder that closes on another thread also joins that thread. Both wait forever.
  - Another handler shuts CUDA down. After that, a thread that still frees pictures gets `CUDA_ERROR_DEINITIALIZED`, and dies in the driver.
  - A decoder that is closed before the exit, or that stays open through it, is fine.
  - Thus vidcut first joins the threads that players and readers leave (`ending::join`, at the end of the CLI's `main` and in `threads::join_closing`).
  - The GUI then ends with `threads::exit_now`, which calls `_exit` on Unix ([threads](design/threads.md#how-the-process-ends)).
  - The threads of the driver carry the name of the thread that started them, for example `vidcut-play-video`.
- **`cuMemAlloc` rounds each allocation up to 2 MiB** (driver 580).
  - A 960×540 P010 frame of FFmpeg's CUDA pool (1.66 MB) takes 2 MiB.
  - CUDA's stream-ordered allocator (`cuMemAllocAsync`) packs pictures within 1.1%.
  - With its release threshold at 0, that allocator gives memory back when a stream is synchronized.
  - `cuda::keep` keeps NVDEC's pictures in memory from that allocator.
- **NVIDIA's driver, opening NVENC, copies the calling thread's nice value onto the process's main thread**.
  - A process without privileges cannot raise that value again.
  - Thus a job at nice 19 would leave the GUI at nice 19.
  - `first::lowest_priority` puts job threads in Linux's idle class (`SCHED_IDLE`) instead. There, the nice value stays the value of the process.
- **NVIDIA's Windows driver has one NT handle per memory object:**
  - Each `vkGetMemoryWin32HandleKHR` of the same memory gives the same handle.
  - If the handle is closed, later exports get a handle that is gone: an import fails with `VK_ERROR_OUT_OF_DEVICE_MEMORY`.
  - If the handle stays open, it keeps the memory after `vkFreeMemory`.
  - `hw::vulkan` exports each memory object of FFmpeg once. It closes the handle when FFmpeg frees the frames context.
  - FFmpeg's own copy of a frame to CUDA exports the same handle, and closes it with the frame.
- **NVIDIA's JPEG decoder gives the picture before on a stream that does not wait for the default stream** (Windows driver 621.24, RTX 4080 SUPER).
  - FFmpeg 9.0.1 maps each NVDEC picture on the stream of its CUDA device (`output_stream` of `cuvidMapVideoFrame`).
  - On a stream made with `CU_STREAM_NON_BLOCKING`, 15 to 33 of 46 JPEG pictures hold the picture before. The frames change from run to run.
  - Image sequences and MJPEG files fail the same way. H.264 on the same stream is correct.
  - On a stream made with `CU_STREAM_DEFAULT`, each JPEG picture is correct, in 8 runs of 4 clips. So is each picture on the default stream itself.
  - Thus the streams of `GpuDecoder::own` wait for the default stream (`cuda::share::Waits`). The player's decoder uses the default stream.
- **FFmpeg's Vulkan ProRes decoder crashes on AMD's Windows driver** (9.0.2, Radeon iGPU, on one thread too).
  - vidcut decodes on Vulkan only on NVIDIA's GPUs (`GpuDecoder::why_not`).
  - A crash cannot be caught. Thus each other vendor needs its own check first.
- **AMD's Direct3D 11 decoder and VideoToolbox lose their way in H.264 sought into an open GOP.**
  - From a keyframe that is not IDR, AMD's decoder decodes a few frames, then repeats one picture.
  - VideoToolbox (FFmpeg 9.0.2) shows other frames after some seeks (`examples/seek_check.rs`).
  - From the start, or from an IDR keyframe, both decoders are correct.
  - `GpuDecoder::why_not` gives such H.264 to the CPU on these decoders.
  - `decode::h264_open_gop` looks for a keyframe that is not IDR.
  - x264 makes open GOPs with B-frames, unless told not to.
- **AMD's Windows driver counts a Direct3D 11 texture imported into Vulkan again against the process for good** (32.0.21042.62, Radeon iGPU).
  - Each `vkAllocateMemory` from a shared NT handle of a texture that was imported before adds twice the texture's size.
  - It adds this to the dedicated GPU memory of the process: the `GPU Process Memory` counter that Task Manager shows.
  - Freeing the memory or the texture takes none of it back.
  - The usage of the adapter and DXGI's `QueryVideoMemoryInfo` do not change.
  - With an import each time a kept picture is shown, the counter passes 70 GB in 18 plays. Each play crosses a cut from a 4K clip to a 1080p clip.
  - A texture imported once and freed leaves nothing, whether the Vulkan memory or the texture is freed first.
  - The viewer copies each picture into a few textures of its own (`hw::d3d11::Shared`).
  - The viewer imports each of these textures once, and keeps them while the window lives.
  - The shareable NV12 and P010 textures of the driver also take less memory than plain ones.
  - For 1 GB of kept pictures, they take 1.4 GB of GPU memory and 1.5 GB private, against 1.9 GB and 3.1 GB.
  - Thus `hw::d3d11::Keeper` keeps pictures in shareable textures.
- **Mesa's VA-API has no exact surface copy** (26.0, radeonsi).
  - `vaCopy` is not implemented.
  - Its video processor shifts levels, even from P010 to P010 at the same size (by up to 9).
  - On Mesa, kept pictures stay the surfaces of the decoder, in a pool that its decoders share (`hw::vaapi::share_frames`).
  - Intel's iHD has an exact `vaCopy`.
  - iHD frees the surfaces that are let go only at its next allocation. Thus the GPU memory of a process (DRM fdinfo) drops late.
- **FFmpeg's copy-down of Intel's VA-API frames is slow**.
  - It reads a copy that the driver makes (`vaGetImage`).
  - On an N150, this takes twice the time of a read of the mapped surface (`vaDeriveImage`).
  - `hw::vaapi::intel_download` maps Intel's surfaces.
  - The mapped memory of Gen7–Gen9 is uncached, and the mapped memory of an Arc card is across the bus.
  - Thus each display times both ways on its first frames, and keeps the quicker way (`hw::vaapi::Ways`).
- **Intel's QSV runtime opens VA-API displays of its own**.
  - libva prints four info lines on stderr for each display.
  - `main` sets `LIBVA_MESSAGING_LEVEL=1` (errors only) on Linux, unless it is already set.

## Operating systems and libraries

- **glibc keeps freed frames' memory** (2.43).
  - Its threshold for mapping a block of its own (128 KiB) rises to the largest block freed, up to 32 MiB.
  - Thus later frames come from heaps that give little back.
  - `buffers.rs` maps planes of its own, and keeps the last 64 MB let go for the next frames.
  - Mapping each plane anew takes a fifth more CPU.
  - A closed decoder's own memory (libdav1d's pool) stays in the heaps.
  - Thus `buffers::give_back` runs `malloc_trim` when the player closes a decoder, at most once a second.
- **Only Linux's idle class is inherited.**
  - On Windows, a thread at the idle priority starts threads at the default priority.
  - On macOS, a thread in the utility QoS class also starts threads at the default.
  - This includes FFmpeg's threads for a job.
  - The threads of the job pool set their own priority (`first::lowest_priority`).
- **`canonicalize` on Windows gives verbatim paths** (`\\?\C:\…`).
  - A verbatim path is not equal to the same path as people write it.
  - `vidcut_core::dirs::canonical` keeps the usual form where it names the same file.
- **Windows separates paths with `/` and `\` both.**
  - Project files keep relative paths with `/` (`portable` in `store.rs`), and read them with the separator of the system.
  - vidcut compares paths as `Path`s, not as strings.
- **A read on a Unix socket on Windows isn't woken by a shutdown** from another thread.
  - Thus a cancelled client would wait forever.
  - On Windows, live control uses named pipes, read with overlapped calls (`ipc::transport`).
- **On Windows a started process inherits every inheritable handle.**
  - The `fopen` of the C runtime opens files as inheritable. x264's two-pass statistics files are among them.
  - While another process holds these files, x264 cannot rename them (`failed to rename`, then `can't open stats file`).
  - std's `Command` always starts a process in this way.
  - Thus Show in Folder asks the shell instead (`gui/file_manager.rs`).
  - Also, a test that starts a process can break the two-pass export of another test in the same binary.
- **macOS's `poll` reports a hang-up only for what it is asked for**.
  - Linux always reports `POLLHUP` and `POLLERR`.
  - Asked for `POLLIN`, a Unix socket hangs up when the peer stops writing.
  - Asked for `POLLOUT`, it hangs up when the peer has closed. `ipc::transport::Stream::peer_gone` asks for `POLLOUT`.
- **WASAPI doesn't move a stream to a new default output** (cpal 0.18).
  - macOS and PipeWire move a stream on the default to the new default device by themselves.
  - On Windows, cpal hears the change, but keeps the stream on the old device.
  - cpal then reports `StreamInvalidated`, or `DeviceNotAvailable` when the old device is gone.
  - `player::output::follow` opens the stream again on the new default.
- **macOS's frame processors list few pixel formats** (macOS 27.2, Apple M4).
  - The frame rate conversion and the super-resolution scaler of `VTFrameProcessor` each list only RGhA, 64-bit RGBA in half floats.
  - Other Macs can list other formats. `vidcut doctor` shows the list of this Mac (`macos_frame_processors`).
  - The frame rate conversion takes RGhA first (`HALF_FIRST`). Why: an 8-bit format would cut 16-bit and HDR pictures to 8 bits.
  - The scaler takes only RGhA (`HALF`). Why: the color fix reads and writes its buffers as half floats.
- **zeno's mask is placed one mask too low** (0.3) when it renders with the origin at the bottom left before it has measured itself.
  - The top that it reports is the bottom edge of the mask.
  - swash measures first. `stroked` in `burn.rs` calls `inspect` before `render` to do the same.
- **cosmic-text shapes each word apart** (0.19).
  - A pair of letters across a space or a hyphen gets no kerning.
  - `kern_words` in `burn.rs` reads the kerning of each such pair with the harfrust of cosmic-text (`cosmic_text::harfrust`). It adds the kerning to the spacing of the pair's first letter.
  - vidcut has no harfrust dependency of its own. A harfrust of another version cannot shape with the fonts of cosmic-text.
- **cosmic-text draws a glyph's coverage, not its color's alpha** (0.19).
  - `Buffer::draw` paints a glyph with alpha 0 at full strength in the RGB of its color.
  - Thus text colored transparent still shows.
  - `lay_out` in `burn.rs` draws only the glyphs that are not marked hidden.
  - It draws underlines in their own colors, which keep their alpha.
- **fontdb keeps only the typographic family name of a font** (0.23).
  - A font can have a family name (name ID 1) and a typographic family name (name ID 16).
  - For example, `SitkaVF.ttf` has `Sitka Text` and `Sitka`, and `calibril.ttf` has `Calibri Light` and `Calibri`.
  - fontdb reads name ID 1 only when the font has no name ID 16. Thus it finds no face for `Sitka Text`.
  - `add_family_names` in `burn.rs` adds the name ID 1 names to each face.
- **cosmic-text takes a family's face only at its exact weight** (0.19).
  - The face must have the weight of the text, or a `wght` axis that includes that weight.
  - Else cosmic-text uses its fallback fonts. For example, the only face of `Marlett` has weight 500, and text at weight 400 does not use it.
  - `with_face_weight` in `burn.rs` gives the text the weight of the face that fontdb selects, or the nearest weight on its axis.
- **cpal's `device_by_id` misses ALSA's devices** (0.18).
  - It adds a device number to the id that it looks for (`sysdefault:CARD=PCH,DEV=0`). The listed ids do not have this number.
  - Thus a device chosen from the list would play on the default, with no message.
  - `output_by_id` finds the device among the listed devices, by its listed id.

## Resolve's OTIO files

These facts come from measurements in Resolve Studio 21.1.1 and 21.1.2, through its scripting API and its Inspector. The measurements set values on clips, export and import OTIO files, and read back stills and a Deliver render.

- **Resolve draws a title read from a file at a pixel a point**, at any picture size.
  - Resolve's own titles have 1/1080 of the height of the picture for a point.
  - At 3840×2160, its own 96-point title is twice as tall as the same title read back from its own export.
  - `otio::titles` reads and writes a point as a pixel of the picture, as the import of Resolve does.
  - Thus a title that vidcut writes looks the same in Resolve, and comes back the same.
  - A title made in Resolve on a picture that is not 1080 lines tall comes in at another size, in vidcut as in Resolve.
- **A bold title in a file has `font-weight:600`.**
  - In Arial, Resolve Studio 21.1.2 draws Bold from 576, 600 and 648.
  - It draws Arial Black from 696 and 700.
  - `otio::titles` writes 600 and reads 600 or more as bold.
- **Resolve draws no stroke from the file on a title read from a file.**
  - It keeps `strokeSize` and `strokeColor`, and writes them back. But it draws nothing at 4, 8 or 16.
  - It drops `-qt-stroke` styles from the rich text.
  - The outline of a title does not show in Resolve.
- **Resolve draws a black edge of 1 pixel on each letter of a title read from a file.**
  - In Resolve Studio 21.1.2, the reader gives each piece of text an outline width of 1.
  - Resolve Studio 21.2 sets Stroke Size 1 and a black color on each title that it reads, whatever the file says.
  - This occurs with `strokeSize` 0, with no `strokeSize`, and with the Stroke group off or not there.
  - The edge goes over all that is under it. The letters are 1 pixel thinner, and they sit half a pixel higher.
  - The same value moves the lines of `<u>`, `<o>` and `<s>` 2 to 3 pixels down.
  - The same title typed in the Inspector, saved and opened again, or read from a `.drt` file has no such edge.
  - The manual does not name this edge.
  - A measurement of a title read from a file removes that edge first.
  - vidcut does not copy this fault. A title draws the same from any source, as a title typed in the Inspector (`otio::titles`).
- **Resolve drops metadata it doesn't know**, which includes the `vidcut` key of the clip.
  - Thus a title comes back from Resolve by its parameters alone.
  - A placed clip comes back by its Transform, Cropping, Dynamic Zoom, Composite and Retime and Scaling alone.
- **Resolve's import loses the own name of a copy of a compound clip** (measured in Resolve Studio 21.2).
  - Its export writes on the `Stack` of each copy the name that the copy shows.
  - Its import gives each copy of one compound clip the name of the first `Stack`.
  - vidcut keeps the name of each `Stack` on its copy.
  - A name that is the name of the compound clip is not kept as the copy's own name. Thus the copy follows a later rename.
- **Resolve's file holds no frame size:**
  - The metadata of its timeline is only `Resolve OTIO Meta Version`.
  - The Transform of a clip (a `Resolve Effect` of type 2), Cropping (3) and Retime and Scaling (22) hold fractions.
  - They list only the parameters that are not at their defaults.
  - `otio::picture` converts them with the shapes of the frame and the source alone (`Shape`).
  - Resolve reads them in the form that `otio::picture` writes: each parameter with its default and empty `Key Frames`.
- **Pan, Tilt and the crop are fractions of Resolve's picture,** not of the frame.
  - Resolve's picture is the source, sized by the `scale` of Retime and Scaling.
  - The scripting API gives `scale` these numbers:
    - 0: the setting of the timeline (fit in a new project).
    - 1: crop.
    - 2: fit.
    - 3: fill.
    - 4: stretch.
  - Crop maps a source pixel to a frame pixel. On pixels that are not square, the value is the crop / (the fit factor × the source width) ([spec §8.15](spec.md#815-transform-and-crop-pp-766768)).
  - A clip at 0 has no Retime and Scaling. The file does not hold the setting of the timeline.
  - Pan is in picture widths to the right, and Tilt in picture heights up.
  - The zoom is across and down the picture.
  - vidcut reads and writes `scale` as the `scaling` of the clip. It writes no `scale` for `project`.
  - Thus Resolve uses its own timeline setting for a clip at `project`.
  - Measured in Resolve Studio 21.2.
  - The picture of a compound clip is the frame.
- **Retime and Scaling also holds `retime process` and `motion estimation mode`.**
  - `retime process` (`UInt`, default 0): 0 Project Settings, 1 Nearest, 2 Frame Blend, 3 Optical Flow.
  - `motion estimation mode` (`UInt`, default 0): 0 Project Settings, 1 Standard Faster, 2 Standard Better, 3 Enhanced Faster, 4 Enhanced Better.
  - Mode 5 is Speed Warp Better, 6 is Speed Warp Faster, and 7 is Metal. Both are `UInt` parameters with `"Key Frames": {}`.
  - `otio::picture::take_retime` extracts these parameters before picture parsing, so unmodeled `Transform` effects do not block retime import.
  - `otio::picture` writes `ClipRetime::Nearest` as 1 and `FrameBlend` as 2.
  - It writes `AiFast` as 3 and 6, `AiSlow` as 3 and 5, and `Macos` as 3 and 7.
  - On import, 3 with 0 to 4 becomes local AI (`Macos` on macOS, `AiFast` elsewhere; deviation X21).
  - A non-zero `motion estimation mode` with `retime process` 0, 1 or 2 stays carried and unplayed.
  - Measured in Resolve Studio 21.2.
- **Resolve zooms and turns about the anchor point,** `transformationAnchorPoint`.
  - The anchor point is from the middle of the picture, in fractions of the picture, y up.
  - Resolve flips about the middle.
  - The middle lands at A − R·S·A, plus the move of Pan and Tilt. A is the anchor, S the zoom and R the turn.
  - vidcut reads the anchor point as `anchor`, and writes it back ([D92](spec.md#12-decisions-on-gaps-and-contradictions)).
  - vidcut keeps the same fraction of the picture. Thus the anchor point stays on the same point of the source.
  - Resolve scales its picture to P about the middle. Then it zooms about the anchor point. P is the size of Resolve's picture.
  - vidcut does both in its `zoom`, about the anchor point. Thus it adds the difference, A·(P − F), to `position`. F is the fitted size.
  - With fit, P is F, and `position` is Pan and Tilt alone.
- **Resolve's Pitch and Yaw are a projective divide about the middle of the picture,** `transformationPitch` and `transformationYaw` ([D93](spec.md#12-decisions-on-gaps-and-contradictions)).
  - The scripting API and OTIO both use −1.5 to 1.5. Usual: 0. The file leaves 0 out.
  - They lean the picture in its own axes, before the zoom and the turn about the anchor, and before Pan and Tilt. Y grows down.
  - Let `(X, Y)` be the offset of a leaned point from the middle of the picture, divided by half the size of the picture.
  - Then `W = 1 − yaw·X + pitch·Y`, and the pre-image is that offset divided by `W`.
  - There is no cosine foreshortening. A 3D rotate-and-project model did not fit the stills.
  - Positive pitch puts the top farther. Positive yaw puts the left closer.
  - Measured on Resolve Studio 21. A 1920×1080 still filled the frame. Zoom was 0.5. Pitch or Yaw was set through the scripting API. Deliver wrote one PNG per value. The silhouette corners of those PNGs are below. The map predicts them to about one pixel when no corner hits the frame edge.
  - Identity corners, top-left first, then clockwise: (480, 270), (1439, 270), (1439, 809), (480, 809).
  - Yaw 0.25: (319, 179), (1343, 323), (1344, 755), (319, 900).
  - Pitch 0.25: (576, 323), (1343, 323), (1600, 900), (319, 900).
  - Yaw −0.5 and Pitch −0.5 were also rendered. Their near corners hit the frame edge, so they were not used as a fit target.
  - An OTIO export of Pitch 0.5 and Yaw −0.75 wrote `transformationPitch` and `transformationYaw` with those values.
  - Six more renders at zoom 0.5 fix the order. Three of them are baselines with the same values and no lean.
  - Of the other three, two have Yaw 0.5: one with the anchor 240 px right, one with Pan 200 px.
  - The third has a 30° turn, the anchor 240 px right and Pitch 0.5.
  - A lean about the middle, before the zoom and the turn, lands the corner marks within about one pixel in all of them.
  - A lean about the anchor in screen axes, after the turn, misses by up to 517 px.
  - A lean about the anchor in the picture's own axes misses by up to 39 px.
  - The earlier render of a 45° turn with Yaw 0.5 agrees with the lean about the middle.
  - The anchor point of the scripting API is in pixels of the source picture.
  - Resolve flips the picture before the lean. A flip mirrors what the leaned shape shows, and keeps the shape.
    - Yaw 0.3 with Flip X put each corner mark on the place of its mirror mark without the flip, within 0.1 px.
    - Pitch 0.3 with Flip Y did the same, top for bottom.
  - Resolve crops the source before the lean. Thus the cut edge leans with the picture.
    - With Yaw 0.3, a crop of 384 source pixels on the left put the edge at x = 609.
    - The lean of the source puts it at 607. A crop of the frame would put it at 672.
  - `place::level` flips and crops in the same order.
- **Resolve's opacity and composite mode are parameters of Composite, a `Resolve Effect` of type 1.**
  - `opacity` (Double) goes from 0 to 100. Its default is 100.
  - `composite mode` (UInt) is 0 for Normal. Resolve leaves it out at Normal.
  - The codes from 1 to 26 are the non-normal modes of `BlendMode::ALL`. Codes 0 to 31 are `CompositeMode::ALL`. `CompositeMode::code` and `CompositeMode::of_code` convert them.
  - The codes from 27 to 31 are Foreground, Alpha, Inverted Alpha, Lum and Inverted Lum.
  - `otio::picture` reads a Composite with a code from 0 to 31 as the composite mode and the `opacity` of the picture.
  - A Composite with a code above 31, or with keyframes on its mode, stays a clip effect.
  - A clip writes one Composite (`otio::picture::joined`). Such a kept Composite gives its mode to the Composite of the picture, unless the picture has a mode.
  - Thus a keyed mode from the file stays when vidcut changes only the opacity.
- **The manual's words for some composite modes do not match Resolve's renders.**
  - Subtract takes the top layer from the bottom layer. The manual says the reverse.
  - Hardlight switches on the top layer, and multiplies at 50% and below. The manual names the bottom layer, and says the reverse.
  - Vivid Light and Pin Light switch on the top layer. The manual names the bottom layer.
  - Hard Mix is a threshold of a + b at 1. The manual says that it adds the layers.
  - Color, Luminosity, Hue and Saturation are not HSL mixes. Spec D75 gives the measured sums.
  - A 16-bit render clips the results to 0..1. Thus Color Dodge and Divide seem to stop at 1 there, and Color Burn at 0. A float render shows no cap.
- **Resolve's Crop Softness is `cropSoftness` (Double) in Cropping,** from −100 to 100.
  - Its keyframes have the form of the keyframes of the crop sides.
  - The renders that fix the fade are in [spec D75](spec.md#12-decisions-on-gaps-and-contradictions).
  - At some whole products, Resolve's fade is one pixel shorter. Softness 5 on a 1920-pixel picture gives 23 pixels, not 24.
  - vidcut rounds down |Softness| × width / 400. Thus it can be one pixel longer than Resolve's fade.
- **Resolve's Pan and Tilt go from −4 to 4.**
  - vidcut writes a picture moved further at 4, and names its clip in the notes of the export.
- **Resolve's Dynamic Zoom is a `Resolve Effect` of type 59.**
  - `dynamicZoomCenter` (POINTF) is the middle of a box. It is from the middle of the picture, in fractions of the picture, y up.
  - `dynamicZoomScale` (Double) is the size of the box as a fraction of the picture.
  - Resolve writes two keys for each, at −s and 1000 − s. s is the first source frame of the clip, in media without a timecode.
  - It writes them on a clip with Dynamic Zoom on or off.
  - A title has an s of 0. Thus its keys are at `0` and `1000`, also on a title later in the timeline.
    - The six titles of `$VIDCUT_TEST_DATA/fixtures/resolve-titles/titles.otio` show this, at 24 fps and g = 86400. Each has a source start of 0 and Dynamic Zoom off.
    - The `dynamicZoomScale` of the first title has the keys 0.8 and 1.0, the default 1.0, and the range 0.01 to 100.
  - For a still, Resolve writes them at −g and 1000 − g. g is the timeline's `global_start_time` in frames.
  - In media with a timecode, s still counts from the first frame of the media, not from its timecode.
    - A clip from frame 90 of media at 10:00:00:00 has its keys at −90 and 910. Its `source_range` starts at 1080090.
  - vidcut writes the keys at −g and 1000 − g. g is the timeline's `global_start_time` in frames.
  - Resolve reads the earlier key as the start and the later key as the end, whatever their times.
  - The box is in fractions of Resolve's picture, as Pan and Tilt are.
  - Thus `otio::picture` reads and writes the box as it is, with any `scale`.
- **Resolve's scripting API has no keyframe calls** (Resolve Studio 21.1.1).
  - No call adds, reads or removes the keyframes of a clip.
  - A scripted value on a parameter with keyframes changes nothing that Resolve shows or plays.
  - A script can change the speed, with or without a stretch of the keyframes, and can export and import OTIO.
  - Thus a measurement sets keyframes in the Inspector and reads them from an OTIO export.
- **A time in `Key Frames` is a whole frame of the clip** (Resolve Studio 21.1.1, on a 1920×1080 timeline at 30 fps that starts at 01:00:00:00).
  - It counts the timeline frames from the first frame of the clip.
  - At speed 1, it is the source frame less the start of the clip's `source_range`.
  - This is so in media with a timecode too. A key on the second frame of a clip is at `1`.
  - At any speed, the source frame is the first frame that the clip shows, plus the time times the speed.
    - At 50%, a key 30 source frames into the clip is at `60`. At 200%, it is at `15`.
  - A clip that plays backward shows its highest source frame first. Frame f shows that frame less f.
    - A render of a clip with numbered frames showed this. vidcut plays a reversed clip in the same way.
    - Thus a key on source frame 239 of a clip that shows 388 first is at `149`.
    - The time of the file runs against the source. Thus `InBez` and `OutBez` change places.
  - A speed change that stretches the keyframes keeps each key on its source frame.
    - On a clip that plays backward, the stretch moves each key by one source frame. This is a bug in Resolve.
    - vidcut keeps each key on its source frame, also on a clip that plays backward.
  - A speed change that does not stretch keeps the numbers in the file. Thus each key stays on its frame of the clip, over another source frame.
  - Resolve reads a file as written. Times, values and eases come back in its Inspector and in its next export.
- **X and Y have keyframes of their own** (Resolve Studio 21.1.1).
  - `transformationZoomX` and `transformationZoomY` each have their own `Key Frames`. So do Pan and Tilt.
  - A keyframe on Position keys X and Y. A later change of X alone adds a keyframe to X only.
  - vidcut keys X and Y together. When both axes have keys, `otio::picture` reads them only on the same frames.
- **With keyframes, `Parameter Value` is not a value of the curve.**
  - It is not the value at the playhead, and not the value of the last keyframe.
  - An import reads the keyframes.
- **Resolve reads a Bezier handle of a keyframe only in its own form.**
  - It writes `"OutBez": {"OutBez": [20.0, 0.0], "Variant Type": "POINTF"}`, and `InBez` in the same way.
  - The first number is the time from the keyframe in frames. The second is a value in the units of the parameter.
  - Resolve refuses the whole timeline when a handle is a bare array. This is so for the volume and for Transform.
  - Resolve also refuses it when a number of a `POINTF` has no decimal point, for example `0` in place of `0.0`.
  - `otio::effects` reads and writes the handles of the volume, the pan and the picture in Resolve's form.
- **Resolve keeps `Enabled` and the `Key Frames` of `Fairlight Clip Pan`.**
  - Resolve Studio 21.2 keeps `Enabled` when false and reads and writes `Key Frames` with `InBez` and `OutBez` handles.
  - A disabled pan plays centered, and an enabled eased pan holds before jumping at the second keyframe, as for volume ([Resolve's renders](#resolves-renders)).
- **Resolve's eases of the picture are Bezier handles, as on the volume.**
  - In the Inspector, Ease Out and Ease In put a flat handle at a third of the gap. Thus the two together play an S-curve.
  - Renders of an eased zoom fit the cubic Bezier curve within 0.0004 of the zoom.
  - A handle raised by 0.2 fits the curve with its value in units of zoom.
- **Resolve plays each ease of Dynamic Zoom as a straight line.**
  - The manual gives four eases: Linear, Ease In, Ease Out and Ease In and Out (p. 768).
  - It keeps `dynamicZoomEase` (UInt: 0 Linear, 1 Ease In, 2 Ease Out, 3 Ease In and Out) and writes it.
  - All four play the same straight line, in stills and in a Deliver render.
  - This is so when the ease is set through scripting and when it is read from a file. Its Inspector menu was not tried.
  - vidcut does not copy this fault. Its eases are curves (`Ease::of`). t is the part of the clip that has played, from 0 to 1:
    - Linear: e = t.
    - Ease In: e = t², slow at the start.
    - Ease Out: e = 1 − (1 − t)², slow at the end.
    - Ease In and Out: e = 3t² − 2t³, slow at the two ends.
  - The box goes from the start box to the end box as e goes from 0 to 1.
  - Thus a clip with an ease other than Linear plays differently in Resolve.
- **Resolve reads a wipe only as its Edge Wipe effect.**
  - It writes a `Custom_Transition` named `Edge Wipe`, with `"Transition Type": "Edge Wipe"` and an effect of type 13 in its metadata.
  - The `angle` parameter (`Int`, −360 to 360, with `Key Frames`) gives the edge. 0 is the bottom, 90 the left, 180 the top and −90 the right.
  - The incoming picture comes in from that edge, and the edge moves at an even speed.
  - `border` is a `Double` from 0 to 0.25, as for a Push. The Inspector shows it times the width of the timeline. `feather` is a `Bool`.
  - Resolve's export also writes `transitionCustomCurvesKeyframes`, as for a Push. With Ease None, it is a straight curve from 0 to 1.
  - Resolve leaves out each value at its default: an angle of 0, no border and no feather.
  - `color` (`Color`, default `#ffffff`) and `ease` (`UInt`, 0 to 4) match Push, measured in Resolve Studio 21.2.
  - Without `Transition Type`, or with the name alone, Resolve makes a cross dissolve. It also does so for a transition with metadata it does not know.
  - Resolve refuses the whole timeline when an `Int` has a decimal point, for example `90.0`.
  - Measured with renders of 24-frame wipes at 0, 90, 180 and −90 degrees, and with an export of Resolve Studio 21.2.
- **The edge of an Edge Wipe is a straight line at its angle.**
  - With y down, the edge moves toward (sin a, −cos a), with a the angle. The incoming picture shows behind the edge.
  - Thus 30 degrees brings the incoming picture in from the bottom-left.
  - The edge moves evenly from the first corner of the frame that it touches to the far corner, by the progress of the transition.
  - With Ease None, the progress at frame f of N frames is f/N, as for a Push.
  - The border is a band of its color, centered on the edge. It is b = `border` × the width of the timeline, in pixels.
  - The band makes the way of the edge b longer. On the first frame, no band shows.
  - With Feather, the band shows no color. It mixes the two pictures linearly, from the incoming picture to the outgoing picture.
  - Measured in Resolve Studio 21.2.
- **Resolve reads the values of Push, Slide and Dip To Color Dissolve only with the type of their effect.**
  - Each is a `Custom_Transition` with the name and the `Transition Type` of the transition.
  - The `Type` of the effect is 50 for Push, 49 for Slide and 11 for Dip To Color Dissolve.
  - Without `Type`, Resolve keeps the transition but drops its values. Thus a dip from such a file plays black.
  - Resolve's own export also writes `transitionCustomCurvesKeyframes`, a straight curve from 0 to 1. Resolve reads a file without it.
  - Resolve writes each preset as a `UInt`, with its default and value only.
  - Resolve 21.1.2 reads an `Int` too, and plays it. But a click on that transition in the timeline closes Resolve.
  - The value is the place of the preset in the Preset menu of the Inspector, from 0.
  - `push style` has four presets, from 0 to 3: Push Left, Push Right, Push Up and Push Down.
  - Push Left moves the pictures right: the incoming picture comes in from the left edge. Push Right moves them left.
  - Push Up moves them up, and Push Down moves them down. The incoming picture pushes the outgoing picture out.
  - `slide style` has six presets, from 0 to 5. The menu names each one "Slide, " and its edges:
    - 0 Left-Right, 1 Right-Left, 2 Bottom-Up, 3 Top-Down, 4 Top-Left and 5 Bottom-Right.
  - Each one comes in from its first edge: left, right, bottom, top, the top-left corner or the bottom-right corner.
  - `transition direction` gives the Direction: 0 In, 1 Out.
  - With In, the incoming picture slides in over the outgoing picture. The outgoing picture stays still.
  - With Out, the outgoing picture slides out the same way over the incoming picture. The incoming picture stays still.
  - `color` (`Color`, `#rrggbb`) is the color of a dip.
  - Resolve leaves out each value at its default: 0, or black.
  - With Ease None, Push and Slide move at an even speed. At frame f of a transition of N frames, the move is f/N of the frame.
  - Thus the first frame of a Push or a Slide shows no move.
  - A dip mixes at (f + 0.5)/N, as a cross dissolve does.
  - No border and no motion blur show at the defaults.
  - Measured with renders of 24-frame transitions between two pictures that code the position of each pixel.
- **Resolve gives Push and Slide a border, a feather, a motion blur and an ease.**
  - The Inspector shows Border 0, Feather off, Color white, Motion Blur 0 and Ease None. Resolve leaves out each value at its default.
  - `border` and `motion blur` are `Double`, with `Key Frames` `{}`, `minValue` 0 and a `maxValue`: 0.25 for the border, 1 for the blur.
  - `feather` is `Bool`. `color` is `Color`, `#rrggbb`, with the default `#ffffff`. `ease` is `UInt`: 0 None, 1 In, 2 Out, 3 In & Out, 4 Custom.
  - The Inspector shows `border` times the width of the timeline. Thus 0.05 shows 27 at 540 × 960 and 96 at 1920 × 1080.
  - On a timeline of 960 × 540, a Border of 20 stores 0.0208. A larger number than the maximum stores 0.25.
- **The border of a Push or a Slide is a band of its color on the moving edge.**
  - The band is b = `border` × the shorter side of the frame. This is 27 pixels for 0.05 at 960 × 540, at 540 × 960, and 54 at 1920 × 1080.
  - In a Push, the band is between the two pictures. In a Slide, it is on the edge of the moving picture that faces the still picture.
  - On a diagonal Slide, the band is on the two edges of the moving picture, and it fills the corner.
  - With the band, each move is p × (S + b) on its axis. p is the progress, and S is the width or the height of the frame.
  - Thus a Push moves the outgoing picture, the band and the incoming picture as one strip. The positions agree within 1 pixel.
- **With Feather, the band shows no color.**
  - The moving picture moves b further, and it covers the band. Its alpha falls linearly from 1 to 0 across the band.
  - In a Push, the two pictures overlap on the band. The band mixes them linearly, from one picture to the other.
  - In the corner of a diagonal Slide, the alpha is the smaller of the two edge ramps.
  - The first frame of the transition shows the outgoing picture with no move. From the second frame, the move above applies.
  - The picture that moves out never moves back. In a Push and in a Slide Out, it moves the larger of 0 and m − b, rounded down.
  - The band and its alpha ramp stay as above. Thus while m is smaller than b, no strip shows at the edge of the frame.
  - Measured with Ease In on 24 frames at 960 × 540 and b = 27. On frames 1 to 4, the Push moved it 0, 0, 13 and 38 pixels. The Slide Out moved it 1 pixel further on frames 3 and 4.
- **Resolve's motion blur of Push and Slide is a box blur along the axis of the move.**
  - At frame f, the box is `motion blur` × 2H × (p(f + 1) − p(f)) long, with H the height of the frame in pixels.
  - Thus with Ease None, the box is 2H/N long at the value 1. It does not depend on the width of the frame or the axis of the move.
  - Renders fit this within about 1 pixel at 960 × 540, 540 × 960 and 1920 × 1080. They had N of 12 and 24, the values 0.5 and 1, and an In & Out ease.
  - For a diagonal Slide, the box goes at 45 degrees, with the length over √2 on each axis. The move itself is not at 45 degrees.
  - The box starts at the sharp edge. For the left, right and diagonal presets, it spreads the way the picture moves.
  - For Push Up, Push Down, Bottom-Up and Top-Down, it spreads against the move. This is so with In and with Out.
  - In a Push, the blur covers the whole frame, the band too. A blurred edge mixes the two pictures linearly. The blur repeats the pixels at the edge of the frame.
  - In a Slide, only the moving picture blurs, and the still picture stays sharp.
  - Across a blurred edge of a Slide, the weight of the incoming picture is c², within 0.02. c is the part of the box that the incoming picture covers.
- **Resolve plays the ease of a Push or a Slide from its curve.**
  - With an ease other than None, Resolve plays the curve `transitionCustomCurvesKeyframes`. Without the curve, the transition stays at its start until its last frame.
  - With Ease None, Resolve plays a straight line, also when the file has a curve.
  - The curve has a key at frame 0 with the value 0 and a key at frame N with the value 1. Its handles are in Resolve's Bezier form.
  - Ease In gives the first key a flat `OutBez` of 0.3 N frames. Ease Out gives the last key a flat `InBez` of −0.3 N. In & Out gives both.
  - This is 7.2 frames for a 24-frame Push with In and In & Out, and 3.6 frames for a 12-frame Push with Out.
  - The progress p(f) is the cubic Bezier curve through the keys and their handles, solved for the frame. Renders fit it within 0.0013.
  - The Inspector shows the curve at the playhead as Transition Curve. The row has a slider, a value from 0 to 1, a keyframe button and a reset button.
  - A change of Ease writes the curve of that ease. A change to Custom keeps the curve that the transition has.
  - Thus a Push from a file without the curve has no keys after a change to Custom. It shows the outgoing picture until its last frame.
  - The keyframe button puts a key at the playhead. The frame of the key counts from the first frame of the transition.
  - A key from the Inspector on a straight part of the curve has no handles. Between two keys with no handles, the progress is a straight line.
  - Measured with keys 0 at frame 0, 0.8 at 12 and 1 at 24. Frames 6, 12 and 18 moved 0.4, 0.8 and 0.9 of the frame.
- **The Transition Curve row of Resolve 21.1.2 edits the curve at the playhead.**
  - With keys, a change of the value puts a key at the playhead with that value. A key that is there gets the value.
  - The playhead can be outside the transition. A change there put a key at frame −12 or 138 of a 24-frame Push.
  - With no keys, a change sets the `Parameter Value` of the curve, and no key. The transition stays at that value: 0.5 held the Push at half the frame.
  - The keyframe button adds a key with the value at the playhead, or removes the key at the playhead. With no keys, the key gets the `Parameter Value`.
  - The removal of the last key keeps the `Parameter Value`. After a key of 0.7 went, the Push stayed at its 0.2.
  - A new key on a curved part cuts the Bezier curve there, and the shape stays. The neighbors get shorter handles.
    - On an Ease In curve of 24 frames, a key at frame 12 cut at u = 0.4138. The `OutBez` of frame 0 went from 7.2 to 2.98.
    - The new key got the `InBez` (−4.397, −0.2008) and the `OutBez` (6.227, 0.2844). Then the typed 0.8 moved the key and its handles.
  - A change of the curve with Ease In or None changes the Ease to Custom. The keyframe button does this too.
  - Reset with Custom gives the straight curve from 0 at frame 0 to 1 at frame N, and the `Parameter Value` 0. With In, it gives the In curve again.
  - The arrows beside the keyframe button move the playhead to the previous or next key.
  - Measured with exports after each change, on 24-frame Push and Slide transitions.
- **A change of the length of a Push scales its curve.**
  - Each key at frame k goes to k × new / old, rounded down. The handles scale by new / old, and they are not rounded. The values stay.
  - Measured with the Duration of the Inspector:
    - 24 to 6 frames put the keys 0, 12 and 24 at 0, 3 and 6. It put the `OutBez` 7.2 of an Ease In curve at 1.8.
    - Then 6 to 5 frames put the key 3 at 2. 5 to 7 kept it at 2, and 7 to 14 put it at 4.
    - 24 to 12 frames put the keys 0.3 at 12 and 0.7 at 13 on frame 6. Resolve kept the first key, 0.3.
- **At a gap, the missing picture of a Push or a Slide shows the tracks below.**
  - It still hides the other picture where it covers it. Thus a Slide In from a clip to a gap covers the clip as it slides in.
  - The tracks below do not move. The other picture moves as usual.
  - Measured at the middle frame of a Push, a Slide In and a Slide Out, into a gap and out of a gap.
- **A Push on a clip with a composite mode moves its pictures before the mode applies.**
  - The tracks below do not move, and the motion blur does not blur them.
  - The mode of the outgoing clip applies to the two moved pictures. The mode of the incoming clip has no effect during the transition.
  - Measured with a gray clip in Add mode over a picture that codes the position of each pixel, with and without motion blur.
- **Resolve does not read back its own OTIO file of an adjustment clip** (measured in Resolve Studio 21.2).
  - Its export has a `MissingReference.1` and an effect of `Type` 74 ([spec §8.24](spec.md#824-adjustment-clips-pp-1145-1154-33753376)).
  - Its import makes an offline clip of that, with the Inspector title "Adjustment Clip".
  - It reads a `GeneratorReference.1` with `generator_kind` "Adjustment Clip" as an adjustment clip that works.
    - That clip takes no Open FX in Resolve. The form that Resolve writes imports offline, so this form is the better one.
  - Thus `otio::generators::adjustment_reference` writes that form, and `otio::generators::is_adjustment` reads both.
- **Resolve writes a Smooth Cut as a `Custom_Transition` with the effect `Morph Dissolve`.**
  - Its name and `Transition Type` are `Smooth Cut`. The `Type` of the effect is 39.
  - `smooth cut mode` (`UInt`) is the Mode: 0 Faster, 1 Better. Better is the default.
  - `smooth cut ai` (`Bool`) is the Speed Warp box. It is on by default.
  - `ease` and `transitionCustomCurvesKeyframes` are as for a Push. Resolve leaves out each value at its default.
- **The Smooth Cut button of Resolve 21.1.2 puts a 24-frame Smooth Cut centered on the edit.**
  - Its Mode is Better, Speed Warp is on and Ease is None.
  - It also puts a 24-frame Cross Fade 0 dB on the linked sound. The Dissolve button puts a Cross Fade +3 dB.
- **A Smooth Cut morphs the two pictures of its edit.**
  - With Better, the two clips play on, as in a cross dissolve. Each frame morphs the frame of one clip into the frame of the other.
  - With Faster, the outgoing picture stays on the first frame of the transition. The incoming picture stays on its last frame.
  - At frame f of N frames, the morph is at min(1, p(f) + 0.5/N). p is the curve of the ease.
  - This fits the renders with Ease None, In and In & Out within 0.0013. The morph is not at p(f + 0.5).
  - Speed Warp off uses optical flow. It moved a bar of a 30-pixel jump to the exact place.
  - When the optical flow does not find the move, the frame is a cross dissolve at the same point. A jump of 150 pixels gave this.
  - Speed Warp on gave one sharp bar for the 30-pixel jump. It smeared the 150-pixel jump.
  - Measured with renders of 24-frame Smooth Cuts between pictures with a bar at known places.

## Resolve's edits

These facts come from measurements in Resolve Studio 21.2, by hand and through its scripting API.

- **The Keyframe button of a locked node on the Fusion page adds a key with the value 0.**
  - A Blur with Blur Size 5 was locked. A click on the Keyframe button of Blur Size added a key, and Blur Size showed 0.
  - One undo took back both. The same click after an unlock added a key at 5.
  - A locked node refuses the other changes of its values: a typed value, a drag and Reset.

  - The tracks stay locked, and no message shows.
  - vidcut does not change a locked track:
    - A clip in the range on a locked track refuses the request, with a message.
    - A cue on a locked subtitle track stays whole.
- **Redo does not give back the legacy Auto Color.**

  - In Resolve Studio 21.1.1 and 21.2, an ease is a Bezier handle on its keyframe.

  - Line spacing moves the lines closer, and lines can overlap (p. 1184).
  - These are measurements in Resolve Studio 21.1.2 from files, with Arial at size 96.

## Resolve's Fusion page

These facts come from measurements in Resolve Studio 21.2, by hand.

- **Paint Mode Replace gives the new mask alone.**
  - Replace gives the same mask as Copy in each read.
  - Where the new mask is 0 and the input mask is 1, Replace gives 0.
  - The manual says that the areas that are zero in the new mask do not change the input mask (p. 2465).
  - vidcut follows the manual: Replace gives n where n is above 0, else the input mask ([spec §8.19](spec.md#the-masks)).
- **The Luminance and the Hue channels of an effect mask swap red and blue.**
  - Luminance gives 0.114 × R + 0.587 × G + 0.299 × B. These are the Rec. 601 weights with red and blue swapped.
  - Hue gives the hue of (B, G, R). Thus red gives 240° and blue gives 0°.
  - Red, Green, Blue, Alpha and Saturation give the correct values.
  - vidcut uses the Rec. 601 luma and the true hue (`fs_picture_mask`, [spec §8.19](spec.md#the-masks)).
- **A mask whose input mask is deleted stops rendering.**
  - After a delete of the mask on its effect mask input, the mask and the tool after it show red names.
  - The viewer keeps the old picture. A change of the mask does not render.
  - After a delete of the mask too, the tool renders again.
  - vidcut renders a mask with nothing on its effect mask input as its own shape ([spec §8.19](spec.md#the-masks)).
- **Auto Render Range gives the whole source, and a change of page keeps a set range.**
  - Auto Render Range sets the range from the first to the last frame of the source. For a clip of 238 frames, the read was −4800 to 12819.
  - Play then goes on past the Out into the tail.
  - A change to the Edit page and back keeps a range of 10 to 30.
  - The manual says that both give back the In and the Out of the timeline clip (p. 1294).
  - vidcut has no render range fields. Its render range is always the In and the Out of the clip ([spec §8.19](spec.md#the-effects-page)). The [todo](todo/effects-page.md) follows the manual.
- **After a failed track, Track Forward fails until a new Tracker is made.**
  - Track Forward from frame 144, after a render range of 10 to 30, renders no frame. A window says "Render did not complete".
  - Then Track Forward from frame 20 fails too. The Console says "MediaOut1 cannot get Parameter for Input at time 20".
  - The names of the Tracker and of MediaOut1 are red. A new Tracker tracks.
  - vidcut keeps no state of a failed track. A start outside the In and the Out gets an error, and the Tracker stays as it was ([spec §8.19](spec.md#the-tracker)).
- **A typed Pattern Width of 1000000 crashes Resolve.**
  - The slider of Pattern Width goes from 0.001 to 0.5. The field keeps a typed 1000000.
  - About 5 seconds later, Resolve 21.2.0.0006 crashes. The project has the state of its last automatic save.
  - vidcut refuses a pattern side outside 0.001 to 0.5, and a side of the search area outside 0.001 to 1 ([spec §8.19](spec.md#the-tracker)).

## Resolve's imports

These facts come from imports in Resolve Studio 21.1.1, by hand and through its scripting API. An item gives another version where it has one.

- **A GIF of one frame with a delay comes in as a video clip.**
  - A GIF of one frame comes in as a still only when its frame has no delay.
  - With a delay, it is a video clip as long as the delay. For example, 0.1 s came in as 3 frames at 25 fps.
  - A WebP of one frame is a still, whatever the duration of its frame.
  - A clip of a few frames of one picture is a blink that the user cannot trim longer.
  - vidcut does not copy this fault. A GIF or WebP of one frame is a still (`VideoStreamInfo`, [D38](spec.md#12-decisions-on-gaps-and-contradictions)).
- **Resolve's import of subtitle files loses text and styles.**
  - A Windows-1252 file shows U+FFFD for each accented letter.
  - Resolve leaves out a WebVTT cue that has no hours in its times.
  - A cue that starts before the previous cue ends starts at that end instead. When nothing of such a cue remains, Resolve leaves it out.
  - `{\an8}` shows as text. Resolve ignores WebVTT `line`, `align` and color classes.
  - From a TTML file, Resolve Studio 21.2 keeps only the cues of the first region. With no named region, it imports nothing.
  - In 21.2, an italic span in a TTML cue makes the whole cue italic. An italic span after a `<br/>` does not come in italic.
  - vidcut does not copy these faults (`subtitles::parse`).
  - It reads UTF-8, UTF-16 and Windows-1252. It reads WebVTT times without hours, and every TTML cue, span and region.
  - It keeps cues that overlap.
  - `{\an8}`, WebVTT `line` and the place of a TTML region put a cue at the top, middle or bottom.
  - WebVTT `align` gives the alignment of the lines.
  - Italic, bold, underline and colors come in from all three formats, on the words that have them.
- **Resolve takes a broken `.cube` file with no message.**
  - In Resolve Studio 21.1.2, the script call `SetLUT` returns True on each of these files:
    - A lower-case size line gives no LUT.
    - A file with no size line gives no LUT.
    - Too few rows give a wrong picture.
    - `LUT_3D_SIZE 1` gives a black picture.
  - The window of Resolve Studio 21.2 shows no message for these files.
  - vidcut does not copy this fault. `media.set` and `project.set` refuse the file and give the reason (`cube::read`).

## transcribe.cpp and its models

- **Qwen3-ASR gives no times** (transcribe.cpp 0.4.2).
  - One segment spans each run.
  - Spread over the speech of a long run, its text drifts from the words.
  - Against Parakeet Ultra's word times on `nasa-speech-1979`, 90% of the cue starts are within:
    - 2.9 s, with pieces of up to 3 min.
    - 2.2 s, with pieces of 30 s.
    - 0.7 s, with pieces of 10 s. This is as close as Whisper large-v3's own phrase times.
  - `transcribe::longest_piece` gives a model without times pieces of 10 s at the most.
- **Qwen3-ASR's GPU memory grows with the length of a run.**
  - On an RTX 4080 SUPER (Vulkan), it takes:
    - 3.6 GB at 30 s.
    - 4.9 GB at 2 min.
    - 8.5 GB at 4 min.
    - 11 GB at 6 min.
    - More than the 16 GB of the card at 10 min.
  - Whisper large-v3 and Parakeet Ultra cut long audio into windows themselves. They hold 2.2 GB and 1.3 GB at any length.
  - `transcribe::longest_piece` sizes the pieces of Qwen3-ASR from half the memory of the GPU (`Gpu::memory_mb`).
- **On a short piece, Qwen3-ASR may guess another language**, and write "呃。" for an English "uh".
  - `transcribe::transcribe` runs the longest piece first, and gives its language to the other pieces.
  - It does not do this when a language was asked for.
- **Silero VAD doesn't hear singing:**
  - On a 38 min rap album, it calls 11% of the sound speech at its usual threshold of 0.5, and 13% at 0.1.
  - Nearly all of that is in two of twelve songs. Thus a lower threshold does not help.
  - Parakeet Ultra transcribes the singing when it hears it.
  - Thus `find: sound` hears all sound above a level instead (`transcript::sounding`).
  - The answer of the voice detection warns when it keeps under a quarter of a range that is mostly loud.
- **Silero VAD is less exact on a GPU:**
  - The F32 products of ggml-metal work in half precision (transcribe.cpp's `silero_vad/model.cpp`).
  - They are about 2e-3 off the reference, against 1e-6 on the CPU.
  - vidcut runs Silero VAD on the CPU (`Backend::Cpu`). There it takes 1.2 s for 29 min of sound.
- **ggml's Vulkan backend builds its pipelines the first time a vidcut build runs a model on a GPU:**
  - With Parakeet Ultra, 10 min of speech takes 3 min the first time.
  - After that, it takes 4 s, because the driver keeps the pipelines.
- **Whisper large-v3 loops in a long run:**
  - In one 4-minute piece of Tears of Steel, it writes "You'll love her." 16 times, over 16 s of lines.
  - It gets these lines right in a piece of 20 s.
  - Its memory does not grow with the length.
  - `transcribe::longest_piece` gives it pieces of 30 s.
- **ggml's Vulkan backend on a Windows without the Vulkan loader:**
  - Where `vulkan-1.dll` is missing, `transcribe::start` starts the CPU backend alone (`init_backends_with`).
- **transcribe.cpp and ggml log to stderr** until a program says otherwise.
  - `transcribe::init` turns that off, unless `VIDCUT_DEBUG` is set.
